# 事件序进展上下文改造方案

编写日期：2026-09-16<br>修订：V2 — 根据评审意见重写结构、排序、字段与截断规则

## 背景

评价 prompt 靠 `progressContext` 给模型提供进展判断的历史对照：

```json
{
  "previousExplanations": ["学生第1轮自讲", "学生第2轮自讲"],
  "previousTeaching": [
    {"content": "提示正文", "questions": ["追问1"], "answers": ["学生回答1"], "followUpContent": "跟进正文"}
  ]
}
```

这套结构有两个缺口：

1. **时序与配对丢失。** 两个扁平数组只记录"存在这些学生文本、存在这些教学事件"，看不出"哪条提示引出了哪句回答"。而 `evaluate_explanation.md` 中"复述教学提示不能直接视为独立进展；应根据学生是否进一步解释或正确应用来判断"是因果判断，依赖这个配对。
2. **角色边界被污染。** `previousTeaching[].answers` 是学生自己产出的内容，却被归在"教学"堆里，正好落在"学生 vs 系统"分界线上。

另外还有一个增长问题：`previousExplanations` 和 `previousTeaching` 都是同 round 全量，无界。

本方案淘汰 `previousExplanations` / `previousTeaching`，统一为**带 role 标注的有序事件序列**，并加截断。

## 目标

- 淘汰两个旧字段。
- 恢复时序：模型能看到"教学 → 学生响应"的顺序。
- 修掉 `answers` 归位矛盾。
- 截断按完整**交互组**执行，不拆散问答。
- 排序使用可靠来源，不比较跨表主键 ID。

## 不做什么

- 不改 `hasProgress` 的定义、动作选择表、状态转换或计数规则。
- 不改 `AIEvaluationOutput` schema 和 `validate_evaluation_relationships`。
- 不改教学器 `ai_teaching.py` 自己的 `teaching_history`。
- 不改已有的 `session_events` 事件类型定义；本方案新增的领域事件（explanation.submitted 等）在阶段二落地，阶段一用现成查询构造 DTO。

```json
    {

      "content": [
        {"questionId": "q1", "question": "闭区间上的最大值应从哪些点中比较？", "answer": "看端点"}
      ],

    },

      "kind": "explanation",
      "content": "我重新看了下，闭区间上的最大值应该看端点。先算 f(0)=2a-1，f(2)=3-2a……",
      "interactionId": "attempt:23"
    }
  ]

```

### 字段说明

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `seq` | int | 是 | 会话级单调递增序号，用于排序。阶段一为合成序号，阶段二来自 `session_events.seq` |
| `actor` | string | 是 | `student` 或 `teacher`，由后端按数据来源确定 |
| `kind` | string | 是 | `explanation`（学生自讲）、`guided_answer`（学生回答追问）、`teaching`（教学或提示正文）、`follow_up`（跟进正文） |
| `content` | string 或 array | 是 | 正文内容。`guided_answer` 类型为数组，其余为字符串 |
| `interactionId` | string | 是 | 事件来源的业务标识，如 `attempt:17`、`support:9`、`submission:23` |
| `replyTo` | string | 否 | 显式回复目标，如 `support:9`。明确配对关系，不依赖相邻位置猜测 |

### 与旧结构的映射

| 旧字段 | 新映射 |
| --- | --- |
| `previousExplanations[i]` | `{"actor":"student","kind":"explanation","content":"..."}` |
| `previousTeaching[k].content` | `{"actor":"teacher","kind":"teaching","content":"..."}` |
| `previousTeaching[k].questions` | 并入同一条 `teaching` 事件的 `content` 中（格式见下文"内容展开规则"） |
| `previousTeaching[k].answers` | 每条回答展开为 `{"actor":"student","kind":"guided_answer","content":[...],"replyTo":"support:N"}` |
| `previousTeaching[k].followUpContent` | `{"actor":"teacher","kind":"follow_up","content":"..."}` |

### 内容展开规则

教学正文（`teaching`）的 `content` 包含正文与引导问题，格式为：

```
先判断抛物线的开口方向，并思考闭区间上的最大值可能在哪里取得

引导问题：
问：闭区间上的最大值应从哪些点中比较？
```

`guided_answer` 的 `content` 是对象数组：

```json
[
  {"questionId": "q1", "question": "闭区间上的最大值应从哪些点中比较？", "answer": "看端点"}
]
```

## 截断规则

**按完整交互组截断，不按事件个数切。**

一个交互组定义为一轮完整的"教学 → 响应"往返，包含三种类型之一：

| 类型 | 组成 |
| --- | --- |
| 完整引导问答 | `teaching` → `guided_answer` → `follow_up`（或直接 teaching → guided_answer） |
| 自讲后直接教学 | `explanation` → `teaching`（不含追问，无 guided_answer） |
| 孤立自讲 | 单独的 `explanation`（首次或终态后） |

截断策略：

1. 从事件序列**尾部向前**扫描，保留最近的 `M` 个完整交互组。默认 `M=5`。
2. 一个交互组只要有一件进入保留窗口，整个组全部保留——不会留下"有回答没问题"或"有问题没回答"的情况。
3. 若全部交互组的累计 token 超过阈值（可选二次截断），从序列头部开始丢弃最早组，直到 token 可接受。
4. 默认配置 `progress_context_max_interactions=5`，走配置项。

## 排序方案

`session_events` 表已经提供会话级单调递增 `seq`（每 session 从 0 开始，每次 `append()` 自动 `seq+1`）。途经的事件类型包括 `user.message`、`context.added`、`model.requested`、`model.responded`、`model.failed`、`state.changed`。

**当前缺口**：`session_events` 尚未写入"教学内容已展示""引导答案已提交""跟进内容已展示"等领域的语义事件。引导答案目前写入 `StudentSubmission`，同时又回填进 `SupportEvent.guided_answers`。

**已实现的替代路径（2026-09-18）**：不新增领域事件，改为给 `support_events` 增加 `created_seq` 列，写入创建时的 `session_events.seq`；自讲的锚点由对应 `user.message` 事件的 `run_id`（`run_session_{sessionId}_attempt_{attemptId}`）反查。投影在锚点齐全时直接按 `seq` 排序，缺少锚点的历史数据回退 `created_at`。下面的阶段一"合成序号"与阶段二"领域事件"因此都不是当前实现。

因此分两阶段实施：

### 阶段一：DTO 投影 + 合成序号

不改 `session_events` 写入链路。`progressContext.events` 继续从现有的 `ExplanationAttempt` 和 `SupportEvent` 查询构建，但排序改用可靠算法：

```
seq = 0
for each (item in sorted([...previous_attempts, ...previous_support], key=lambda x: x.created_at)):
    yield {seq, ...}
    seq += 1
```

`created_at` 是精确到秒的时间戳，来自同一时钟（应用服务器），**不依赖跨表 ID 比较**。数据库记录精度不满足时（同一秒多条记录），回退到 ID 排序——这种场景仅出现在同一事务内批量写入时，此时业务顺序已由写入顺序隐含。

**示例代码**

```python
def build_progress_context(
    *,
    previous_attempts: list[ExplanationAttempt],
    previous_support: list[SupportEvent],
    max_interactions: int,
) -> dict[str, list[dict[str, object]]]:
    raw: list[tuple[datetime, int, str, object]] = []   # (created_at, fallback_id, type, record)

    for item in previous_attempts:
        if item.confirmed_text:
            raw.append((item.created_at, item.id, "attempt", item))
    for item in previous_support:
        raw.append((item.created_at, item.id, "support", item))

    raw.sort(key=lambda x: (x[0], x[1]))   # created_at asc, id asc as tiebreaker

    events: list[dict[str, object]] = []
    seq = 0
    for created_at, fallback_id, rec_type, record in raw:
        if rec_type == "attempt":
            events.append({
                "seq": seq, "actor": "student", "kind": "explanation",
                "content": record.confirmed_text,
                "interactionId": f"attempt:{record.id}",
            })
            seq += 1
        elif rec_type == "support":
            _append_support_events(events, record, seq)
            seq = len(events)    # reset seq after batch append
    return {"events": _truncate_by_interaction(events, max_interactions)}
```

`_append_support_events` 展开一个 `SupportEvent` 为最多 4 个事件（`teaching`、`guided_answer`（每条问答一条）、`follow_up`），并设置 `replyTo`。

### 阶段二：领域事件写入 + `session_events.seq` 投影

向 `session_events` 新增以下事件类型：

| 事件类型 | data 字段 | 写入时机 |
| --- | --- | --- |
| `explanation.submitted` | `{attemptId, confirmedText}` | 提交自讲确认文本时（现有 `user.message` 附近） |
| `teaching.given` | `{supportEventId, supportType, content}` | 教学/提示/纠错展示时 |
| `guided.question.asked` | `{supportEventId, questions}` | 追问展示时 |
| `guided.answer.submitted` | `{supportEventId, sourceEventId, answers}` | 学生提交引导答案时 |
| `followup.given` | `{supportEventId, content}` | 跟进内容展示时 |

改造后，`progressContext.events` 直接从 `session_events` 过滤这些领域事件类型并按 `seq` 排序得到，不再需要查询 `ExplanationAttempt` 和 `SupportEvent`。

阶段二代价较大，涉及事件契约定义、写入链路改造、以及已有历史的迁移。如果当前项目的 `hasProgress` 误判率在可接受范围内，可以先做阶段一。

## Prompt 改动

`backend/app/prompts/evaluate_explanation.md` 的"进展判断"部分改写：

```markdown
- 首次提交没有历史时（`progressContext.events` 为空），只要当前文本包含与本题有关的有效推理、依据或局部结果，就返回 `true`；只说不知道、只表达疑问或机械复述题目时返回 `false`。
- 后续提交需结合 `progressContext.events` 判断学生本轮是否新增有效推理、纠正错误、补充依据或给出合理替代解法。`events` 是有序事件序列：`actor=student` 表示学生原始产出（自讲或对追问的回答），`actor=teacher` 表示系统给出的教学（提示正文或跟进正文）。判断时关注位于最后一条 `teacher` 事件之后的 `student` 事件，确认新增内容是否独立产出而非复述 `teacher` 事件中的内容。`replyTo` 字段标明事件回复的目标，可用于确定教学与回答之间的配对关系。
- 复述教学提示不能直接视为独立进展；应根据学生是否进一步解释或正确应用来判断。
- 完成态仍返回 `hasProgress`，但完成规则优先于进展判断。
```

### 截断函数 `_truncate_by_interaction`

```python
def _truncate_by_interaction(
    events: list[dict[str, object]], max_interactions: int
) -> list[dict[str, object]]:
    """从序列尾部按交互组保留，保证不拆散问答。"""
    if max_interactions <= 0 or not events:
        return []

    # 标记每条事件所属的交互组编号：从尾部向前扫描
    # 一个交互组的起始边界：actor=teacher 的 teaching/follow_up 事件（组的第一个事件）
    # 或孤立的 student explanation
    group_id = [0] * len(events)
    current_group = 0
    in_answer_section = False
    for i in range(len(events) - 1, -1, -1):
        ev = events[i]
        kind = ev.get("kind", "")
        actor = ev.get("actor", "")
        if actor == "teacher" and kind in ("teaching", "follow_up"):
            current_group += 1
            in_answer_section = True
        elif actor == "student" and kind == "explanation":
            if not in_answer_section:
                current_group += 1
            # explanation 前若有 teacher 事件，已计入前一组
            in_answer_section = False
        group_id[i] = current_group

    # group 0 = 最旧的组（可能跨过开头不完整），group 1..N = 后续各组
    # 取 group >= (max_group - max_interactions + 1) 的事件
    if not group_id:
        return []
    max_group = max(group_id)
    keep_threshold = max(0, max_group - max_interactions + 1)
    return [ev for i, ev in enumerate(events) if group_id[i] >= keep_threshold]
```

## 合理性批判

1. **`created_at` 排序在批量写入时退化到 ID 排序。** 同一秒内多条记录的先后由数据库自增 ID 决定，虽不比 `seq` 精确但在实际场景中基本等价。若你的数据库 `created_at` 精度为秒级（SQLite 默认），同一个事务内写入的 attempt 和 support 的时间戳相同，回退到 ID 排序——此时 attempt ID 和 support ID 仍不同表，实际上是在比较跨表 ID。这是一个真实风险。如果实际数据中同一个事务同时创建 attempt 和 support 的场景频繁出现且顺序重要，应在阶段二用 `session_events.seq` 解决，阶段一不做完人承诺。

2. **按交互组截断的实现复杂度。** `_truncate_by_interaction` 需要在不知道组边界的情况下扫描事件序列标记分组。V1 方案只按事件数量切，实现简单但会拆散问答；V2 按交互组切更合理，但函数本身更容易出错（边界判定 `in_answer_section` 的状态机逻辑需要仔细测试）。

3. **阶段二的写入改造成本被推迟了，但没消失。** 现有的"写入 → 回填"模式（`StudentSubmission` + `SupportEvent.guided_answers`）已经有两份写入路径，再加领域事件就是第三份。如果后续继续涨，应该考虑合并：放弃 `SupportEvent.guided_answers` 回填，改用 `session_events` 中过滤 `guided.answer.submitted`。但这需要重建读数据的地方（`get_pending_guided_support`、教学历史等）。本方案只承诺不做阶段二以外的改动。

4. **`guided_answer` 的 `content` 是数组，与其它事件类型不一致。** 这是特意做的取舍：`question_id + question + answer` 的结构需要在 AI 侧保留，不能只展开为纯文本。代价是模型读事件时要处理两种 `content` 类型。

5. **`replyTo` 对教学器的教学历史没用。** `replyTo` 只在评价器的 `progressContext` 中生效，教学器 `ai_teaching.py` 用自己的 `teaching_history`（最近 9 条 `SupportEvent`），不看也不需 `replyTo`。评价器与教学器的历史口径不一致会长期存在，这不是本方案能统一的。

## 与现有架构的关系

- 数据层：阶段一不涉及表结构变更；阶段二向 `session_events` 新增事件类型，不改已有表结构。
- 规则层：`teaching_decision.py`、`teaching_cycle.py` 不变。
- AI 能力层：只改评价 prompt 的上下文结构。
- 审计：`ModelRequestBlocks.session_context` 会将新 `progressContext` 记入 request snapshot。
