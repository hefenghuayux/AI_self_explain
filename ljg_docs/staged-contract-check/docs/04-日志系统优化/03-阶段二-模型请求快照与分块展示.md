# 阶段二：模型请求快照与分块展示数据

## 1. 阶段目标

在每次真实 AI 外部调用之前构造结构化请求快照，并将该快照与实际传输 payload 一起保存到对应 `ExternalCallRecord`。快照必须能回答：

- 使用了什么评价或教学规则；
- 提供了哪些题目和评分材料；
- 注入了哪些当前会话上下文；
- 是否注入跨会话教学记忆；
- 学生本次输入是什么；
- 重试时加入了哪些校验错误；
- 模型客户端实际收到的 messages 和 response format 是什么。

本阶段保存数据并通过 Structured Event 暴露，不改变实际模型消息角色，不完成最终前端样式。

## 3. 数据库任务

在 `external_call_records` 增加：

```text
request_snapshot JSON NULL
```

同时增加：

```text
transport_status VARCHAR NOT NULL
validation_status VARCHAR NOT NULL
validation_errors JSON NULL
ai_evaluations.external_call_record_id INTEGER NULL
```

规则：

- AI 评价和 AI 教学支持的新记录必须写入快照。
- ASR 记录不适用时保持数据库 `NULL`。
- 旧记录迁移后允许为 `NULL`，不得伪造无法还原的历史请求。
- upgrade 增加新字段，并将旧 `status` 迁移为 `transport_status`；`AI_SCHEMA_ERROR` 可确定为传输成功、校验失败，其他无法可靠判断的历史校验状态使用 `UNKNOWN`。
- downgrade 将旧 `status` 恢复为 `transport_status` 后删除新增字段；校验状态在旧 Schema 中无法表达，必须在迁移说明中明确该信息会丢失，不得重新把 Schema 错误伪装成传输失败。
- 新记录不再使用一个 `status` 同时表达传输和输出校验；完成迁移后删除旧 `status` 字段，避免两个近义状态长期并存。
- 新 `AIEvaluation` 必须引用产生该输出的 `ExternalCallRecord`；历史评价记录允许为空，不按时间或文本指纹猜测关联。

状态组合固定为：

- 超时、连接错误或 HTTP 错误：`transport_status=ERROR`、`validation_status=NOT_RUN`；
- 模型返回成功但 Schema 不合法：`transport_status=SUCCESS`、`validation_status=INVALID`；
- 模型返回成功且 Schema 合法：`transport_status=SUCCESS`、`validation_status=VALID`；
- ASR：按实际传输结果保存，`validation_status=NOT_RUN`；
- 历史记录无法判断：`validation_status=UNKNOWN`。

## 4. 请求快照数据契约

### 4.1 公共结构

```json
{
  "schemaVersion": "1.0",
  "purpose": "AI_EVALUATION",
  "promptVersion": "evaluation-v1",
  "blocks": {},
  "transport": {},
  "privacy": {
    "containsStudentContent": true,
    "containsAnswerMaterial": true,
    "containsMemory": false
  }
}
```

### 4.2 语义分块

`blocks` 使用固定边界：

- `systemInstructions`：提示词模板中的规则与输出约束；
- `questionContext`：题目、标准答案、评分点、常见错误、替代解法、分层提示、引导问题和完整解析；
- `sessionContext`：round、supportCountRound、coveredPointsCurrentRound 等当前会话确定性状态；
- `memoryContext`：真正注入的跨会话教学记忆；当前没有时省略；
- `userInput`：自讲、主草稿、疑问或子问题答案；
- `retryContext`：上一轮 Schema 校验错误；首次调用为空列表或省略适用明细。

不得把 `sessionContext` 改名为 memory。当前系统没有跨会话教学记忆注入时，Structured Event 省略 `memoryContext`，人读投影负责显示“本次未注入记忆”。

### 4.3 实际传输结构

`transport` 是真实传输快照，至少包含供应商实际收到的：

- `model`
- `messages`
- `response_format`

第一版实际传输保持当前行为：

```json
{
  "model": "deepseek-chat",
  "messages": [
    {
      "role": "user",
      "content": "渲染后的完整提示词"
    }
  ],
  "response_format": {
    "type": "json_object"
  }
}
```

数据库中的 `transport` 字段名和结构必须与实际发送的 payload 一致，不能只保存前端展示用的 camelCase 结构。界面可以把 `systemInstructions` 显示为“评价规则”，但必须同时显示实际传输角色为 `user`，不能误导为已经使用 system message。

## 5. 请求构造任务

### 5.1 统一输入对象

将 `AIModelClient.evaluate(prompt, schema)` 调整为接收一个经过校验的请求对象。请求对象同时提供：

- 用于审计的结构化 snapshot；
- 用于 HTTP 请求的 transport payload。

不得分别手写“审计快照”和“实际 payload”，避免二者漂移。HTTP client 必须直接使用 snapshot 中已经确定的 transport 字段，或使用同一对象的确定性序列化结果。

### 5.2 评价请求

`_render_prompt` 不再只返回字符串，而是构造评价请求对象：

1. 读取评价规则模板；
2. 分离规则、题目材料、会话上下文、学生确认文本和校验错误；
3. 使用现有模板规则生成实际完整 prompt；
4. 将 prompt 写入单个 `user` message；
5. 返回包含 blocks 和 transport 的请求对象。

评价服务每次 Schema 重试都重新构造快照，确保 `retryContext.validationErrors` 与实际 prompt 一致。

### 5.3 教学支持请求

`generate_support` 和 `assess_guided_answers` 使用同一快照契约，但 `purpose` 分别为：

- `AI_SUPPORT`
- `GUIDED_ANSWER_ASSESSMENT`

学生输入块按实际业务类型保存，不把 mainDraft、doubtText 和 guided answers 混成无法区分的字符串。

### 5.4 外部调用持久化

`record_external_call` 增加必需的 AI `request_snapshot` 参数：

- 传输成功：保存请求快照和 raw response；
- HTTP 错误：保存请求快照、错误和可能存在的 raw response；
- 超时/连接错误：仍保存已经发起的请求快照；
- Schema 校验失败：对应实际调用记录必须能够找到该次请求快照。

不增加“缺快照时自动构造空对象”的兜底逻辑。AI 调用缺少快照应明确报错；只有 ASR 类型允许不适用。

## 6. Structured Event 任务

AI 外部调用事件增加 `data.requestSnapshot`。同时保留：

- provider
- model
- attemptNumber
- duration
- transport/validation status
- raw response 的现有处理策略

每个 AI `ExternalCallRecord` 固定投影一个 `ai.call.*`；`validation_status` 为 `VALID` 或 `INVALID` 时再投影一个 `ai.output.*`。评价类输出通过 `AIEvaluation.external_call_record_id` 合并评价数据和引用，不再由两套来源重复生成同一个校验事件。

`privacy` 必须标记请求快照包含哪些受限内容。完整请求不能写入普通 `application.log`。

`privacy` 至少区分：

- `containsStudentContent`、`containsAnswerMaterial`、`containsMemory`：实际包含的受限内容；
- `redactedFields`：没有直接写入快照的敏感字段。

## 7. 测试任务

### 7.1 请求一致性测试

使用 Mock/Spy AI client 验证：

- snapshot `transport.messages` 与实际传给 HTTP client 的 messages 完全一致；
- response format 完全一致；
- snapshot model 与实际 model 一致；
- 不允许修改 prompt 后忘记同步快照。

### 7.2 评价测试

- 首次评价快照包含评价规则、题目材料、sessionContext 和 confirmedText。
- 首次评价不伪造 memoryContext。
- Schema 重试的第二次快照包含上一轮 validationErrors。
- transport timeout 记录仍包含请求快照。
- request snapshot 不包含 API key、Authorization header 和 OTLP 等秘密。

### 7.3 教学支持测试

- 请求提示支持时能够区分 mainDraft 和普通支持请求。
- 提出疑问时能够区分 mainDraft 和 doubtText。
- 子问题评估能够保存 questions 和 answers。
- 每种 purpose 与实际 prompt 模板对应。

### 7.4 审计测试

- 新 AI 调用事件包含 requestSnapshot。
- 旧数据库记录 request_snapshot 为 NULL 时，trace 能明确表示历史请求不可用，但不能伪造内容。
- ASR 事件不出现 requestSnapshot。
- API 只对现有教师审计路由开放；当前按单教师、本地 Demo 处理，不扩展多租户会话归属权限。
- 旧 AI 记录没有快照时，事件显式输出 `requestSnapshotAvailability: NOT_RECORDED`；ASR 事件输出 `NOT_APPLICABLE`，不能仅依靠字段缺失推断。

## 8. 阶段验收标准

- 所有新 AI 外部调用都有请求快照。
- 每次重试有独立快照和 attemptNumber。
- 快照能够分块还原模型收到的全部内容。
- 快照的 transport 与实际发送 payload 一致。
- 当前实际消息角色仍为单个 user message，模型行为不因日志改造改变。
- transport payload 的字段和值与实际发送请求一致。
- API key 和 Authorization header 不进入快照。
- 数据库迁移 upgrade/downgrade 测试通过。

## 9. 明确不做

- 不把实际请求改成 system/user 两条消息。
- 不实现跨会话教学记忆；只预留并如实记录 memoryContext。
- 不接入向量检索、知识图谱或外部追踪平台。
- 不在普通运行日志打印完整快照。
- 不实现最终分块视觉样式；该内容属于阶段三。

## 10. 风险与不足

1. 完整请求快照会复制题目和学生内容，数据库增长速度高于当前实现；第一版先保证审计完整性，保留周期需要在真实部署前制定。
2. 自由 JSON 字段便于保存不同请求类型，但数据库无法逐字段约束；因此必须由 Pydantic Schema 校验后再持久化。
3. 旧记录无法可靠重建实际请求，只能明确标记不可用。根据当前题目和 session 重新渲染会制造虚假审计证据，禁止这样回填。
