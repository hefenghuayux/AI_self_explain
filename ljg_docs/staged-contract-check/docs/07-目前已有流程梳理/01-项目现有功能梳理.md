## 2. 项目当前定位

当前项目是一个带登录和题库管理的 AI 自讲 Demo。学生选择题目后，可以用文本或语音输入自己的理解；系统评价学生最终确认的文本，再按确定性规则决定完成、追问、提示、纠错、人工复核或展示解析。

AI 负责评价和生成教学内容。会话状态、支持次数、连续无进展次数、两轮上限和暂停恢复由后端规则层控制，前端只负责展示和提交操作。

## 3. 当前用户与权限

### 3.1 学生

- 注册学生账号、登录、退出和自动恢复已保存的登录状态。
- 查看未归档题目，按学段、学科和题干关键词筛选并分页。
- 从题目开始自讲，恢复同一题目的未结束会话，或主动重新创建一条新会话。
- 使用文本输入、实时语音转写、提交自讲、请求提示、提出疑问、回答子问题和申诉。
- 查看当前反馈、学习进度、完整解析（在允许的阶段）和历史时间线。
- 在稳定阶段暂停会话，之后恢复到暂停前阶段。

### 3.2 教师

教师拥有学生的学习功能，并额外可以：

- 新增、查看、编辑未归档题目。
- 查看已归档题目。
- 归档和恢复题目。
- 在会话页进入运行日志，查看轨迹账本、时间线和单条记录详情。

教师账号不通过公开注册创建。公开注册接口固定生成 `STUDENT` 角色。

### 3.3 人工处理人员

系统会保存学生申诉或 AI 无法可靠判断的具体原因，并在学生时间线中显示已申请人工复核。当前没有离线复核、派单、接管和复核后更新状态的界面。

## 4. 功能总览

| 功能域 | 当前能力 | 主要入口 | 当前边界 |
| --- | --- | --- | --- |
| 账号 | 学生注册、登录、退出、当前用户、登录状态保存 | `/login`、`/register` | 没有找回密码、角色管理和教师公开注册 |
| 题库 | 题目 CRUD、归档/恢复、详情、分页、筛选、关键词检索 | `/`、`/questions/new`、`/questions/{id}` | 题目来源导入是一次性导入，没有自动同步 |
| 会话 | 创建/恢复/重新自讲、版本校验、按用户隔离 | `/sessions/{id}` | 只允许已登录用户访问自己的会话 |
| 自讲教学 | 文本提交、评价、追问、提示、纠错、子问题、疑问、申诉 | 会话页 | 教学模型和 ASR 真实网络调用需环境配置 |
| 语音 | 浏览器录音、实时 ASR、回填可编辑草稿、提交到原操作 | 会话页 | 移动端麦克风需要安全上下文，真实 ASR 仍需外部服务验证 |
| 两轮规则 | 有效支持计数、无进展升级、展示解析、第二轮、上限终止 | 后端规则层 | 阈值来自配置，当前默认值需以运行配置为准 |
| 时间线 | 学生可见提交、评价、支持、解析和人工复核事件 | `/sessions/{id}` | 只展示面向学生的内容，不展示全部原始日志 |
| 运行日志 | 按运行展示轨迹账本、时间线、搜索折叠和单条记录详情 | `/sessions/{id}/logs` | 当前入口和 API 仅教师可用；Surface 与 Trace 不再是页面入口 |

## 5. 账号与权限流程

### 5.1 注册与登录

1. 用户在注册页提交用户名、密码和姓名。
2. 后端校验必填字段、密码至少 6 位和用户名唯一性，成功后固定创建学生账号。
3. 用户回到登录页提交用户名、密码和“记住登录状态”选项。
4. 登录成功后后端创建认证会话，前端保存当前用户；勾选记住时将令牌写入 `localStorage`。
5. 重新打开前端时，路由守卫尝试用保存的令牌调用 `/api/auth/me`；失效则清除令牌并回到登录页。

后端入口：`POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`、`POST /api/auth/logout`。

### 5.2 页面权限

前端路由对题目录入、题目详情和会话日志设置 `teacherOnly`；后端题目写操作使用教师依赖，日志路由整体使用教师依赖。学生即使绕过页面也不能通过后端直接新增、编辑、归档或恢复题目。

## 6. 题库流程

### 6.1 查询和展示

题目列表首次加载动态筛选选项和第 1 页题目。查询支持：

- `page`、`page_size`，前端提供 20、50、100 条每页选项。
- `grade_period`、`subject` 和 `keyword`，多条件按 AND 组合。
- 教师可切换 `include_archived=true` 查看归档题目；学生只能看到未归档题目。

列表只返回摘要字段，题干按统一 HTML 净化模块渲染；标准答案和完整解析通过单题详情接口读取。题目按是否配置非空评分点优先，再按创建时间和 ID 倒序。

### 6.2 题目录入与维护

教师可以保存题干、标准答案、评分点、常见错误、替代解法、分层提示、提示子问题和完整解析。评分点材料可为空，后端根据材料确定评价模式：

| 模式 | 当前判定 | 当前完成规则 |
| --- | --- | --- |
| `FULL_RUBRIC` | 有非空评分点列表 | 评价正确性和评分点完整性，按完整规则推进 |
| `BASIC` | 无评分点，但有标准答案或完整解析 | AI 评价正确性，正确即完成 |
| `AI_GENERAL` | 评分点、标准答案和完整解析均无 | AI 依据题干评价，正确即完成；针对性支持受限 |

归档是软归档：历史会话仍可读取，归档题目不能编辑，也不能创建新会话；教师可以恢复。

### 6.3 题库导入

项目已有从原题库只读导入到 `self_explain_questions` 的实施记录，保留题干 HTML 和来源字段，不自动生成缺失的 AI 评价材料。导入完成后源库变化不会自动同步到 AI 自讲库。

## 7. 自讲会话流程

### 7.1 创建、恢复和重新自讲

1. 学生或教师在未归档题目上点击“开始自讲”。
2. `POST /api/sessions` 检查题目存在、未归档和当前用户归属。
3. 同一用户再次进入同一题目时，后端可以恢复未结束会话；传入 `restart=true` 时创建新会话，不覆盖旧会话。
4. 新会话从 `WAIT_INITIAL_CHOICE` 开始，保存当前轮次、计数、草稿、覆盖评分点和版本号。

会话读取和时间线接口会再次校验 `session.user_id`，不能通过修改 ID 读取其他学生的会话。

### 7.2 当前入口与输入

当前 `SessionView` 已经去掉“会 / 不会”两个用户可见按钮。新会话的内部初始阶段仍然是 `WAIT_INITIAL_CHOICE`，但它只是兼容后端状态的中间阶段：

- 用户在“自讲”分段直接提交文本，前端自动调用 `initial-choice`，选择 `KNOW`，随后提交自讲。
- 用户在“自讲”分段开始录音，前端同样先自动选择 `KNOW`，再开始采集语音。
- 用户在“我有疑问”分段提交文本或开始录音，前端自动选择 `HAS_QUESTION`，随后调用疑问接口。
- 后端仍保留 `POST /api/sessions/{id}/initial-choice`，也接受 `NOT_KNOW`，但当前前端没有“不会”入口；直接调用该接口属于 API 兼容能力，不应写成当前页面流程。

提交自讲后，主输入框内容会保存为不可变的 `confirmedText`。AI 只评价这份最终确认文本，ASR 原文只作为草稿和过程记录。会话处于 `WAIT_STUDENT_ACTION` 时，用户再次提交自讲，前端先调用 `/continue` 回到 `CAPTURING_INPUT`，再提交新的文本。

会话页的进度主摘要按当前轮已覆盖评分点计算，显示为“已讲清 X 个关键点，还差 Y 个”；本轮辅助支持次数降为次要信息，不作为主要视觉焦点。没有评分点的 `BASIC` 或 `AI_GENERAL` 题目按 0 个关键点计算。

### 7.3 文本评价与教学动作

提交自讲后，后端进入 `AI_EVALUATING`，评价服务返回严格结构化结果：正确性、完整性、覆盖评分点、缺失评分点、错误证据、固定 `confidence=1` 和人工处理原因。

`backend/app/rules/teaching_decision.py` 根据评价组合确定后续动作：

| 评价结果 | 默认动作 |
| --- | --- |
| `CORRECT + COMPLETE` | 完成当前轮 |
| `CORRECT + INCOMPLETE` | 聚焦追问 |
| `WRONG + COMPLETE` | 纠错 |
| `WRONG + INCOMPLETE` | 纠错并追问 |
| `UNCERTAIN` | 申请人工复核，保留继续自讲能力 |

模型输出会经过字段、评分点集合、原话引用和 `needHumanReason` 关系校验。结构错误有限重试；仍失败时保存原始响应和校验错误，并回到可继续操作的稳定阶段。

### 7.4 提示、追问、子问题和疑问

- 聚焦追问 `ASK_FOCUSED_QUESTION` 不计有效支持。
- `GIVE_HINT`、`GIVE_CORRECTION`、`CORRECT_AND_ASK` 是计数支持。
- 后端仍提供 `POST /api/sessions/{id}/request-support`，用于根据主草稿请求提示；当前 `SessionView` 的分段入口没有单独的“我不会，给我一点提示”按钮，直接调用该接口属于现有 API 能力。
- “我有疑问”保存独立疑问文本，由教学支持模型判断是简单知识点、关键步骤问题还是完整答案请求；语音疑问同样先回填草稿，再由原疑问操作提交。
- 需要追问时，评价后的教学模型必须生成恰好一个子问题；请求提示或关键步骤疑问的 `GUIDED_QUESTIONS` 支持通常生成 2 至 3 个子问题。学生在“回答子问题”输入块逐题提交答案，答案评估不会再次增加支持次数。
- “AI 说错了”要求填写理由，保存申诉提交和人工复核事件，不调用 AI 对申诉进行二次裁决，也不增加有效支持次数。

### 7.5 每一步调用的系统提示词

以下“系统提示词”指 `backend/app/prompts` 中的模板。代码把模板保存到模型请求快照的 `blocks.systemInstructions`，当前实际传输时将“模板 + JSON 上下文”放在一条 `role=user` 消息中，并使用 `response_format: {"type":"json_object"}`；因此审计名称和 HTTP role 需要分别理解。

四个模板的原文开头如下，后面的完整约束、JSON Schema 和上下文占位符以仓库文件为准：

| 模板文件 | 原文开头 | 主要职责 |
| --- | --- | --- |
| `evaluate_explanation.md` | “你是 AI 自讲 Demo 的结构化评价器。只能基于提供的题目材料和学生最终确认文本评价，不能根据音频或 ASR 转写判断。” | 判断正确性、完整性、评分点覆盖和错误证据 |
| `generate_teaching.md` | “你是 AI 自讲 Demo 的教学内容生成器。后端已经完成答案评价、状态判断、计数和教学动作选择。” | 在后端指定动作下生成反馈和受限数量的子问题 |
| `generate_support.md` | “你是 AI 自讲 Demo 的教学支持生成器。根据以下 JSON 上下文决定本次可见教学内容。” | 处理请求提示、疑问、完整答案拒答和无进展支持 |
| `assess_guided_answers.md` | “你是 AI 自讲 Demo 的子问题作答评估器。根据以下 JSON 上下文，逐题判断学生作答。” | 逐题评估子问题答案并生成整合引导 |

#### 步骤 A：评价学生最终自讲

触发入口：`POST /api/sessions/{id}/text-attempts`。后端先保存 `confirmedText`，再调用 `AIEvaluationService`。

提示词文件：`backend/app/prompts/evaluate_explanation.md`。

提示词要求可以概括为：

1. 只能依据题目材料和学生最终确认文本评价，不能依据音频或 ASR 原文。
2. 只返回严格 JSON，字段为 `correctness`、`completeness`、`coveredPoints`、`missingPoints`、`errorEvidence`、`confidence`、`needHumanReason`。
3. 覆盖点和缺失点必须逐字引用题目评分点；错误证据必须逐字引用学生确认文本。
4. 只做事实评价，不生成反馈、提示、子问题、下一动作，也不判断状态、支持次数和阈值。
5. `UNCERTAIN` 必须填写人工处理原因；`confidence` 固定为数字 `1`。

评价结果由确定性规则映射为动作：

| 评价结果 | 是否再次调用模型 | 教学模型允许动作 | 子问题数量 |
| --- | --- | --- | --- |
| `CORRECT + COMPLETE` | 否 | 直接完成 | 0 |
| `CORRECT + INCOMPLETE` | 是 | `ASK_FOCUSED_QUESTION` | 恰好 1 个 |
| `WRONG + COMPLETE` | 是 | `GIVE_CORRECTION` | 0 |
| `WRONG + INCOMPLETE` | 是 | `CORRECT_AND_ASK` | 恰好 1 个 |
| `UNCERTAIN` | 否 | 申请人工复核 | 0 |

#### 步骤 B：根据评价生成教学反馈

触发条件：步骤 A 得到合法评价，且确定性决策的 `should_generate=true`。`CORRECT + COMPLETE` 和 `UNCERTAIN` 不触发这一步。

提示词文件：`backend/app/prompts/generate_teaching.md`。

后端把题目材料、当前确认文本、最新评价、当前轮覆盖点、目标评分点、错误证据、最近两次自讲摘录、最近支持记录和规则指令放进 `TeachingContext`。提示词明确要求：

- 只能执行 `instructionFromRules.allowedAction`。
- 只返回 `content` 和 `questions`。
- `ASK_FOCUSED_QUESTION`、`CORRECT_AND_ASK` 必须返回一个问题；`GIVE_HINT`、`GIVE_CORRECTION` 必须返回空问题数组。
- 遵守 `doNotRepeat`、`doNotReveal` 和 `responseGoal`，不能直接复述标准答案或完整解析。
- 每次生成的 `content` 都要从当前学生输入中逐字引用一句有价值的表达，并紧接着说明它具体推进了哪个评分点或解题步骤；引用使用引号，不能改写或虚构。

这里的子问题只在评价后的动作是 `ASK_FOCUSED_QUESTION` 或 `CORRECT_AND_ASK` 时产生。生成成功后保存 `SupportEvent`；有子问题时阶段进入 `WAIT_GUIDED_ANSWERS`，没有子问题时回到 `WAIT_STUDENT_ACTION`。达到支持上限时，确定性代码直接展示完整解析，不调用这一步生成局部支持。

#### 步骤 C：用户请求提示或提出疑问

触发入口：`/request-support` 或 `/ask-doubt`。两者都会调用 `AISupportService.generate_request`，区别是 `doubtText` 是否为空。

提示词文件：`backend/app/prompts/generate_support.md`。

提示词要求模型在严格 JSON 中返回 `action`、`coveredPoints`、`missingPoints`、`content` 和 `questions`，并按输入类型分流：

| 支持模型动作 | 触发情形 | 子问题 |
| --- | --- | --- |
| `REFUSE_FULL_SOLUTION` | 学生直接索要完整答案 | 空数组，只说明提供局部帮助 |
| `SIMPLE_DOUBT_ANSWER` | 疑问是简单知识点 | 空数组，直接回答 |
| `GUIDED_QUESTIONS` | “不会”请求或关键步骤疑问 | 一般为 2 至 3 个引导问题，不给出问题答案 |
| `CURRENT_STEP_ANSWER` | 当前轮连续无进展达到阈值，后端传入 `forceCurrentStep=true` | 空数组，只回答当前一个步骤 |

代码对 `GUIDED_QUESTIONS` 至少要求一个问题，对其他动作要求问题数组为空。请求提示的 `GUIDED_QUESTIONS` 先记录一次请求进展；如果连续无进展达到配置阈值，会再次调用同一提示词并强制 `CURRENT_STEP_ANSWER`。这次当前步骤回答不生成子问题。

支持模型的 `content` 同样必须逐字引用 `mainDraft` 或 `doubtText` 中一句有价值的学生表达，并说明该表达具体推进的评分点或步骤。

#### 步骤 D：评估学生对子问题的回答

触发入口：`POST /api/sessions/{id}/guided-answers`，且当前阶段必须是 `WAIT_GUIDED_ANSWERS`。学生可以分多次提交，直到当前支持事件中的所有问题都有答案。

提示词文件：`backend/app/prompts/assess_guided_answers.md`。

提示词要求：

1. 对已发送的每个问题各返回一次 `CORRECT`、`INCORRECT` 或 `INCOMPLETE`。
2. `content` 给出整合引导；错误或不完整时只解释对应问题答案，并说明如何利用已有信息继续解题。
3. 不新增题目材料中没有的公式、条件、关系或中间结论，也不泄露完整解析。
4. `content` 必须逐字引用 `mainDraft` 或 `answers` 中一句有价值的学生表达，并说明该表达具体推进的评分点或解题步骤。

所有问题回答齐全后才调用该提示词；结果保存到 `guided_answers` 和 `follow_up_content`。该调用不创建新的支持事件，也不重复增加 `supportCountRound`。

### 7.6 两轮与完成

后端按当前配置判断支持上限。达到阈值时直接展示完整解析，不发送触发阈值的那次局部支持：

- 第一轮达到上限后展示解析；学生确认理解后隐藏解析并进入第二轮完整自讲。
- 第二轮达到上限后再次展示解析，状态为 `STOPPED_LIMIT`。
- 正确且完整完成时状态为 `COMPLETED`，完成方式记录为 `INDEPENDENT`、`WITH_SUPPORT` 或 `AFTER_SOLUTION`。
- 进入第二轮时重置当前轮覆盖集合和无进展计数，全会话覆盖集合保留用于审计。
- 当前轮连续无新增评分点达到配置阈值后，下一次聚焦追问升级为计数的 `GIVE_HINT`。

### 7.7 暂停和恢复

只允许在等待学生操作的稳定阶段暂停。评价或 ASR 处理中请求暂停时，先等待当前调用结束。恢复后回到暂停前的流程阶段，并保留草稿、轮次和计数。

### 7.8 语音输入

浏览器端 `VoiceRecorder` 采集音频并通过 WebSocket 连接实时 ASR。转写结果会回填到对应的主输入、疑问、子问题答案或申诉输入框；学生可以修改后使用原操作提交，不存在独立的语音确认阶段。

后端保存原始音频文件、ASR 原始文本、语音目标和关联尝试。ASR 失败保持会话可继续，并退回最近可重试的语音输入阶段。

## 8. 当前状态与过程记录

### 8.1 业务状态

当前接口和前端可见状态包括：

| 状态 | 当前含义 |
| --- | --- |
| `IN_PROGRESS` | 会话仍可继续自讲或请求支持 |
| `COMPLETED` | 正确且完整完成 |
| `STOPPED_LIMIT` | 第二轮支持上限触发，已展示解析 |
| `PAUSED` | 暂停，等待恢复 |
| `NEED_HUMAN` | Schema 和前端保留的人工处理状态；当前 `UNCERTAIN` 与申诉主要保持 `IN_PROGRESS` 并记录人工复核原因 |

流程阶段包括 `WAIT_INITIAL_CHOICE`、`CAPTURING_INPUT`、`AI_EVALUATING`、`WAIT_STUDENT_ACTION`、`WAIT_GUIDED_ANSWERS` 和 `SHOWING_FULL_SOLUTION`。

### 8.2 学生时间线

`GET /api/sessions/{session_id}/timeline` 返回学生可见的提交、评价、支持、完整解析和人工复核事件。刷新页面后可重新读取；技术错误不会把原始异常细节直接展示给学生。

### 8.3 Session Event Log

每个运行事件按会话 `seq` 保存，并通过 `run_id`、父事件和请求 ID 关联输入、模型调用、状态变化与结果。教师可查询：

- `GET /api/sessions/{id}/events`
- `GET /api/sessions/{id}/events/{seq}`
- `GET /api/sessions/{id}/surface`
- `GET /api/sessions/{id}/trajectory`
- `GET /api/sessions/{id}/trace?run_id=...`

日志是运行事实和领域记录引用，不反向决定业务状态、计数或阈值。

## 10. 未实现或不应从当前代码推断出的能力

- AI 对学生申诉的二次复核。
- 离线人工复核、派单、人工接管和复核后状态更新。
- 自动生成题目、评分点、量规、变式题和隔天掌握检测。

- 大规模并发、成本优化、完整生产级账号管理、找回密码和细粒度权限。
- 真实 ASR、真实教学模型和真实部署环境的稳定性结论。代码提供调用边界和测试替身，但外部服务结果仍依赖环境配置。

## 11. 可验证性与当前风险

### 11.1 已有验证

后端测试覆盖账号、题目 CRUD/归档、列表分页与筛选、会话创建与重启、评价结构、教学动作、支持计数、暂停恢复、时间线、实时语音输入和事件日志投影；前端测试覆盖登录状态、题库页面、HTML 净化、自讲页面和日志页面。

这些测试主要验证本地代码和替身服务。它们不能单独证明真实模型、ASR 网络、移动端麦克风权限、生产数据库迁移或部署安全。

### 11.2 当前必须注意的风险

1. 需求基线把人工复核定义为过程事件，而 Schema/前端仍保留 `NEED_HUMAN` 状态。继续扩展状态时必须先统一契约，避免把 `UNCERTAIN` 错当成新的终态。
2. `BASIC` 和 `AI_GENERAL` 能提高题目可用率，但缺少人工评分点时，支持内容和结果的可审计性低于 `FULL_RUBRIC`。
3. 日志视图可接触学生文本和模型上下文，当前只开放教师；在扩大访问范围前需要单独定义敏感字段策略。
4. 记住登录状态依赖浏览器本地令牌，适合 Demo，不能直接等同于生产环境的安全会话方案。

## 12. 合理性批判与不足

1. 本文按代码事实整理，能避免把设计计划写成已交付功能，但“已实现”仍不等于真实外部服务和生产部署已验收，读者需要结合验证边界理解结论。
2. 当前功能总览把题库导入列为已有流程，导入记录证明了实施结果，但源库连接、目标库状态和数据量会变化，后续盘点仍应重新抽样。
3. 将 `NEED_HUMAN` 兼容状态单独标出可以保留现有前端和 Schema 的事实，但会让读者同时看到两套语义；后续若修订需求，应优先收敛状态契约。
4. 文档没有替代接口文档、字段说明和阶段方案；它只提供现状索引，具体字段和规则仍应回到 `docs/01-基本功能/00-需求与Demo范围.md` 等权威文档核对。
