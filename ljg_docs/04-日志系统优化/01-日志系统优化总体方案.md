# 日志系统优化总体方案

## 1. 文档状态

- 状态：已确认，待分阶段实现
- 适用范围：AI 自讲 Demo 后端运行日志、会话审计 Structured Event、前端全链路审计页和审计导出文件
- 目标版本：Structured Event Schema `3.0`
- 实施原则：每次只实施一份阶段文档，不提前完成后续阶段

## 2. 背景与当前问题

当前系统已经具备三类记录：

1. `backend/app/core/logging.py` 输出运行日志到 stdout 和 `data/logs/application.log`。
2. `ExplanationAttempt`、`StudentSubmission`、`StateTransitionEvent`、`ExternalCallRecord`、`AIEvaluation`、`SupportEvent` 等表保存业务事实。
3. `AuditTraceService` 将多张业务表投影为 `/audit/trace`、`trace.jsonl` 和 `audit.md`。

现有方向正确，但存在以下问题：

- 人读日志和机器事件使用同一种冗长 JSON 表现形式。
- `student.input.confirmed` 并不对应独立用户动作。文本提交时，`ExplanationAttempt`、`StudentSubmission` 和 `StateTransitionEvent` 在同一事务中产生，审计投影却把它们展示成三次动作。
- `durationMs`、`errorType`、`errorMessage`、引用 ID 等不适用字段大量输出为 `null`。
- 每条事件重复输出相同的 `source.service` 和 `source.module`；其中 `audit_trace` 只是投影模块，不是行为真正发生的位置。
- 模型调用只保存响应，没有保存实际请求；无法回答“模型收到了哪些规则、题目材料、会话上下文、记忆和学生输入”。
- 当前评价请求实际上只有一个 `user` message。提示词规则和上下文被拼成一个字符串，不能在不改变模型行为的情况下声称已经使用真正的 system message。
- 前端虽然有业务分组和完整审计两个视图，但仍然以事件为中心，不能把一次提交压缩成少量可读业务步骤。

## 3. 设计目标

### 3.1 人读 Trace Log

人读 Trace Log 用于开发者和教师快速理解发生了什么，不作为稳定数据契约。

它包括：

- stdout 和 `application.log` 的紧凑单行运行日志；
- 前端会话全链路的业务步骤视图；
- `GET /api/sessions/{session_id}/audit/business-trace` 人读业务步骤投影；
- `audit.md` 人读导出。

默认只展示动作、结果、状态变化、耗时和错误。技术事件、关联 ID、模型请求块和原始 JSON 按需展开。

### 3.2 机器消费的 Structured Event

Structured Event 用于程序检索、统计、审计和后续追踪集成。

它包括：

- `GET /api/sessions/{session_id}/audit/trace`；
- `output/audit/sessions/{session_id}/trace.jsonl`。

Structured Event 保留原子事实、稳定事件名、关联关系和重试信息，但不输出无意义空字段。

### 3.3 权威业务记录

现有业务表继续作为权威事实来源。不得新增一份通用事件账本复制相同事实，也不得让 Trace Log 或 Structured Event 反向决定状态机。

状态转换、计数和阈值仍由确定性后端规则执行。AI 只负责评价、生成教学内容和复核。

## 4. 目标架构

```text
业务请求
  -> 确定性服务与仓储
     -> 权威业务记录
        -> Structured Event v3（机器契约）
           -> 前端业务 Trace（人读投影）
           -> trace.jsonl（机器导出）
           -> audit.md（人读导出）

业务请求
  -> Python logging
     -> stdout 紧凑文本
     -> application.log 紧凑文本
```

运行日志和会话审计解决不同问题：运行日志用于定位进程、HTTP 和异常；会话审计用于解释一次教学会话的业务过程。两者通过 `requestId`、`sessionId` 关联，但不合并成同一份全量文件。

## 5. 事件精简决策

| 当前事件 | Structured Event v3 | 人读 Trace | 决策理由 |
| --- | --- | --- | --- |
| `student.input.confirmed` | 删除 | 删除 | 文本模式没有独立确认动作，与提交重复 |
| `student.input.submitted` | 重命名为 `student.explanation.submitted` | “学生提交自讲” | 准确表达用户动作，并合并 attempt/submission 引用 |
| `state.transitioned` | 保留 | 折叠进对应业务步骤 | 状态机权威证据不能删除 |
| `ai.call.completed/failed` | 保留 | 折叠进“AI 评价/教学调用” | 记录传输成功、失败、重试和耗时 |
| `ai.output.validated/validation_failed` | 保留 | 与对应 AI 调用合并展示 | 传输成功不代表输出通过业务校验 |
| `voice.capture.completed` | 改为 `voice.transcription.completed` | “语音转写完成” | 当前记录代表音频落盘和 ASR 完成，不只是采集完成 |
| `audio.persisted` | 保留 | 折叠进语音步骤 | 文件证据有审计价值，但不需要独占业务行 |
| `support.generated` | 保留 | “教学反馈已生成” | 代表最终提供给学生的内容 |

删除 `student.input.confirmed` 只影响审计投影，不删除 `ExplanationAttempt` 模型，也不改变评价、语音和外键关系。

## 6. Structured Event v3 契约

### 6.1 顶层结构

```json
{
  "schemaVersion": "3.0",
  "producer": {
    "service": "ai-self-explain-backend",
    "version": "0.1.0"
  },
  "sessionId": 42,
  "generatedAt": "2026-08-10T10:20:30Z",
  "summary": {},
  "events": []
}
```

`producer` 在 trace 顶层只出现一次。单条事件不再重复固定的 `source`。

### 6.2 事件公共字段

```json
{
  "eventId": "submission-18",
  "sequence": 4,
  "occurredAt": "2026-08-10T10:20:30Z",
  "eventName": "student.explanation.submitted",
  "severity": "INFO",
  "correlation": {
    "sessionId": 42,
    "requestId": "request-1"
  },
  "operation": {
    "name": "SELF_EXPLANATION",
    "kind": "STUDENT_INPUT"
  },
  "result": {
    "status": "SUCCESS"
  },
  "data": {},
  "references": {
    "studentSubmissionId": 18,
    "attemptId": 13
  }
}
```

### 6.3 可空字段规则

- 不适用字段不输出，不输出 `null` 占位。
- 成功且没有耗时的结果只输出 `status`。
- 有耗时时输出 `durationMs`。
- 失败时才输出 `error` 对象。
- `references` 只包含实际存在的 ID。
- `privacy` 只在事件含受限内容或脱敏字段时出现，并明确区分“实际包含的受限内容”和“未直接输出的脱敏字段”。
- 不编写通用递归清理空值的兜底函数；每类事件在构造时只加入适用字段。

失败结果示例：

```json
{
  "status": "ERROR",
  "durationMs": 30001,
  "error": {
    "type": "AI_TIMEOUT",
    "message": "AI 请求超时"
  }
}
```

### 6.4 JSONL 独立记录信封

API 中的事件依赖 trace 顶层 `schemaVersion` 和 `producer`，事件体不重复这些字段。JSONL 每行需要能够脱离文件上下文独立解析，因此使用记录信封：

```json
{
  "schemaVersion": "3.0",
  "producer": {
    "service": "ai-self-explain-backend",
    "version": "0.1.0"
  },
  "sessionId": 42,
  "event": {
    "eventId": "submission-18",
    "eventName": "student.explanation.submitted"
  }
}
```

JSONL 中的 producer 因“每行独立”要求而重复，但不属于事件业务字段，也不再使用固定且误导性的 `source.module: audit_trace`。

### 6.5 关联字段与导出语义

- `StudentSubmission` 和 `SupportEvent` 保存 `request_id`；
- `StateTransitionEvent` 保存可选的 `related_support_event_id`；
- 新记录必须写入适用关联字段，旧记录允许为空且不得按时间猜测；
- `SELF_EXPLANATION` 投影为 `student.explanation.submitted`，其他提交类型继续使用 `student.input.submitted`；
- 提交事件中的学生内容只保存字符数和 SHA-256，完整文本只进入模型请求快照；
- JSONL 每次从数据库全量重建并原子替换，因为语音草稿等投影可能在后续提交后被合并，不能继续使用增量追加。

## 7. 模型请求快照

### 7.1 保存位置

在 `external_call_records` 增加 `request_snapshot` JSON 字段，并将传输结果与输出校验结果分开保存。每一次真实 AI 请求保存独立快照，包括失败和重试请求。ASR 调用不伪造 AI 请求快照，该字段不适用时保持数据库空值，并在事件中标记为 `NOT_APPLICABLE`。

### 7.2 快照结构

```json
{
  "purpose": "AI_EVALUATION",
  "promptVersion": "evaluation-v1",
  "blocks": {
    "systemInstructions": "评价规则原文",
    "questionContext": {},
    "sessionContext": {},
    "memoryContext": null,
    "userInput": {},
    "retryContext": {}
  },
  "transport": {
    "model": "deepseek-chat",
    "messages": [
      {
        "role": "user",
        "content": "实际发送的完整文本"
      }
    ],
        "response_format": {
      "type": "json_object"
    }
  }
}
```

快照必须同时保存语义分块和实际传输内容：

- `systemInstructions` 是评价或教学规则的语义块；第一版仍明确记录其实际传输角色为 `user`。
- `sessionContext` 是当前会话确定性状态，不得称为记忆。
- `memoryContext` 只保存真正注入的跨会话教学记忆；当前未注入时，人读界面显示“本次未注入记忆”。
- `userInput` 保存本次学生输入。
- `retryContext` 保存 Schema 重试时加入的校验错误。
- `transport` 是真实传输快照，保存模型服务实际收到的 `model`、`messages` 和 `response_format` 字段；不得使用仅供展示的规范化字段替代真实 payload。
- `transport.messages` 必须与模型客户端实际收到的请求完全一致。

### 7.3 模型行为边界

本轮日志优化不把现有单个 `user` message 改成真正的 `system + user` messages。消息角色调整属于模型行为变更，必须在独立模型回归评测后实施。

### 7.4 外部调用状态边界

`ExternalCallRecord` 将传输和输出校验作为两个独立结果保存：

- `transportStatus`：`SUCCESS` 或 `ERROR`；
- `validationStatus`：`VALID`、`INVALID`、`NOT_RUN` 或历史无法判断时的 `UNKNOWN`；
- `validationErrors`：仅在输出校验失败时保存校验错误列表。

超时、连接错误和 HTTP 错误属于传输失败；模型服务已返回但应用 Schema 校验失败属于传输成功、输出校验失败。Structured Event 分别投影 `ai.call.*` 与 `ai.output.*`，不能将后者误报为传输失败。

## 8. 隐私与访问边界

模型请求快照可能包含：

- 学生原始输入；
- 标准答案、完整解析和评分点；
- 当前会话状态；
- 未来注入的跨会话记忆；
- 校验失败信息。

因此必须遵守：

1. 完整内容只进入数据库审计、教师审计 API、教师前端和本地审计导出。
2. 普通运行日志不得写入完整提示词、学生文本、标准答案或记忆。
3. Structured Event 明确标记包含受限模型内容。
4. 上线多教师或多学校环境前，必须补充会话归属授权，不能只验证教师角色。
5. `trace.jsonl` 和 `audit.md` 被视为敏感本地文件，不进入 Git。

当前阶段明确按单教师、本地 Demo 的安全边界实现；该假设不能外推为多租户生产授权已经完成。

## 9. 分阶段实施顺序

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| 阶段一 | Structured Event v3、事件删除/重命名、空字段和 producer 调整、关联字段和 v3 全量导出 | 无 |
| 阶段二 | 模型请求快照、传输/校验独立状态、数据库迁移、请求与快照一致性 | 阶段一 |
| 阶段三 | 紧凑运行日志、前端业务 Trace、模型请求分块、Markdown 导出 | 阶段二 |
| 阶段四 | 全链路测试、历史导出迁移验收、文档更新和交付检查 | 阶段一至三 |

每个阶段完成后都必须单独汇报实现、执行测试、检查 Git diff，并按项目规则提交本阶段代码。不得在一个阶段中提前实现后续功能。

## 10. 总体验收标准

- 一次文本自讲不再产生 `student.input.confirmed`。
- 人读 Trace 中，一次正常自讲默认压缩为 2 至 3 个业务步骤。
- Structured Event 仍能区分提交、状态转换、AI 传输、输出校验和教学支持。
- API 和 JSONL 不再输出不适用的 `null` 字段。
- 固定 `source` 不再在每条事件中重复。
- 每次 AI 调用都能查看与实际请求一致的语义分块和 transport messages。
- 当前未注入跨会话记忆时明确显示“本次未注入记忆”。
- 普通运行日志保持紧凑，不泄露模型请求内容。
- 前端桌面和移动端均完成视觉验证。
- 旧 v2 导出不会与 v3 事件混写。
- 每次导出均从权威数据库记录全量重建并原子替换，不使用事件 ID 增量追加。
- 前端和 Markdown 使用同一后端 `business-trace` 业务步骤投影，不各自实现聚合规则。

## 11. 合理性批判与不足

1. Schema v3 是不兼容变更。当前没有确认的外部消费者，因此选择直接升级；如果未来已有第三方依赖，需要重新设计版本协商。
2. 保存完整请求快照增加隐私和存储压力，但它是证明“实际发给模型什么”的必要审计证据；应通过授权和保留周期治理，而不是只保存无法还原内容的哈希。
3. 同一学生文本会同时存在于业务提交记录和模型请求快照中。这是有意的审计冗余：前者证明学生提交内容，后者证明外部调用内容，两者不能互相替代。
4. 暂不拆分实际 system/user role 可以避免日志重构改变模型行为，但分块中的 `systemInstructions` 在第一版只是语义分类，界面必须明确实际传输角色。
5. 全量导出会增加单次写入成本，但当前投影包含事件合并和删除，增量追加无法保持最新事实；在本地 Demo 范围内优先保证可重建性。
