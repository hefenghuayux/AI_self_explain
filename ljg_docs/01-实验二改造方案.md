# 自讲请求拆分：实验二改造方案

编写日期：2026-09-16

## 目标

把当前“评价与教学一次调用”的自讲主链路拆成两个请求：

1. `evaluate_explanation` 负责评价、进展判断和本轮原因分类；
2. 后端校验评价结果，并用确定性规则决定状态和教学动作；
3. 只有确实需要教学内容时，才调用 `generate_teaching`；
4. `generate_teaching` 只生成面向学生的 `content` 和 `questions`，不得重新评价或改变后端动作。

原因分类只由阶段一产出：`generate_teaching.md` 中可复用的原因组表、原因选择证据约束和诊断与验证约束全部迁入 `evaluate_explanation.md`，阶段二只消费已确认的 `main_reason`、`other_reasons`、`judge_reason`，不重新生成或覆盖。

本次只调整学生提交自讲后的 `EXPLANATION` 路径。`HELP`、`GUIDED_ANSWER`、完整解析展示、申诉和语音转写流程不在本轮范围内。前端响应结构保持不变。

## 目标调用链

```text
学生提交 confirmedText
  -> evaluate_explanation
     -> correctness
     -> completeness
     -> coveredPoints
     -> hasProgress
     -> main_reason
     -> other_reasons
     -> judge_reason
  -> 后端 Schema 与字段关系校验
  -> 后端更新覆盖点和无进展计数
  -> 后端确定状态与 allowedAction
     -> 已完成或触发支持上限：直接落库，不调用教学模型
     -> 需要教学：调用 generate_teaching
        -> content
        -> questions
  -> 后端校验教学输出与 allowedAction 的关系
  -> 创建 SupportEvent 并返回原有 SessionResponse
```

阶段一成功、阶段二失败时，不重新评价。后端只重试 `generate_teaching`；教学请求在重试上限内仍失败，则保留已经保存的评价记录，并把会话转入现有人工处理路径。这样可以避免同一次学生输入产生互相矛盾的两份评价。

## 数据契约

### 阶段一：评价输出

```json
{
  "correctness": "WRONG",
  "completeness": "INCOMPLETE",
  "coveredPoints": [1, 2],
  "hasProgress": true,
  "main_reason": "知识应用问题",
  "other_reasons": [],
  "judge_reason": "学生已正确计算两个端点值，但没有把最大值条件完整用于分类讨论。"
}
```

关系约束：

- `correctness` 只判断学生已经表达的内容是否含错误；漏答或漏步骤由 `completeness` 表示。已有内容均正确但未完成时，允许 `CORRECT + INCOMPLETE`。
- `coveredPoints` 继续使用评分点编号。不再单独输出 `errorEvidence`，错误依据统一由 `judge_reason` 承载，需要引用学生原话时须逐字摘自 `confirmedText`。
- 非终态必须返回 `main_reason` 和 `judge_reason`；`other_reasons` 没有候选项时返回空数组。
- `CORRECT + COMPLETE` 时固定返回 `main_reason: null`、`other_reasons: []`、`judge_reason: null`。
- `hasProgress` 只由模型根据当前文本和实际提供的历史判断。后端用它更新计数和选择动作，不让模型直接修改业务状态。
- `main_reason`、`other_reasons`、`judge_reason` 只在阶段一产出，阶段二不得重新生成或覆盖。

### 后端动作规则

按以下顺序匹配，顺序本身属于业务规则：

| 顺序 | 条件 | 结果 |
| --- | --- | --- |
| 1 | `CORRECT + COMPLETE` | 完成当前学习流程，不调用阶段二 |
| 2 | 非评分点评价模式且不能生成可审计支持 | 保留现有人工处理逻辑，不调用阶段二 |
| 3 | 达到本轮支持上限 | 展示完整解析，不调用阶段二 |
| 4 | `hasProgress = false` | `allowedAction = GIVE_HINT` |
| 5 | `correctness = WRONG` | `allowedAction = GIVE_CORRECTION` |
| 6 | `completeness = INCOMPLETE` | `allowedAction = ASK_FOCUSED_QUESTION` |

这张表沿用当前提示词的判断优先级。`WRONG + INCOMPLETE + hasProgress=true` 会先进入 `GIVE_CORRECTION`，不会同时追问。若后续确实需要恢复 `CORRECT_AND_ASK`，应先修改状态转换表和计数规则，再改代码，不能让模型自行组合动作。

### 阶段二：教学输出

```json
{
  "content": "教学正文",
  "questions": []
}
```

阶段二上下文必须包含：题目材料、学生当前文本、实际教学历史、阶段一完整评价结果（含已确认的 `main_reason`、`other_reasons`、`judge_reason`），以及后端生成的 `instructionFromRules.allowedAction`、`doNotRepeat`、`doNotReveal` 和 `responseGoal`。原因分类以 `latestEvaluation` 为唯一来源，阶段二只按其组织 `content` 和 `questions`，不得重算或覆盖。

后端关系校验：

- `ASK_FOCUSED_QUESTION` 必须恰好返回一个问题；
- `GIVE_HINT`、`GIVE_CORRECTION` 的 `questions` 必须为空数组；
- `content` 必须为非空字符串；
- 阶段二不得返回评价、原因、进展、动作、状态或计数字段，额外字段由 Schema 拒绝。

## 修改步骤

### 第一步：先拆提示词

修改文件：

- `backend/app/prompts/evaluate_explanation.md`
- `backend/app/prompts/generate_teaching.md`

先明确可复用内容的迁移方向。原 `generate_teaching.md` 中的原因组及验证方式表、原因选择与证据约束、诊断与验证约束从阶段二迁出，全部并入 `evaluate_explanation.md`；阶段一负责产出已确认的 `main_reason`、`other_reasons`、`judge_reason`，阶段二只消费结果，不重新生成、不重排、不覆盖。迁移完成后两份提示词负责的字段和职责不重叠。

`evaluate_explanation.md` 的调整：

1. 删除教学动作选择表、教学内容约束以及 `content`、`questions` 的生成要求。
2. 保留正确性、完整性、评分点覆盖判断；删除 `errorEvidence` 字段，错误依据不再单独输出结构化引用，统一写入 `judge_reason`（需要引用原话时须逐字摘自 `confirmedText`）。
3. 增加 `hasProgress`、`main_reason`、`other_reasons`、`judge_reason` 的明确契约；迁入原 `generate_teaching.md` 的原因组及验证方式表、原因选择与证据约束、诊断与验证约束，作为阶段一分类原因的唯一依据。
4. 写清 `CORRECT + INCOMPLETE` 的含义，避免实验二中同一答案在不同调用方式下出现 `CORRECT` 与 `WRONG` 的口径漂移。
5. 结构重试时只修正格式和字段关系，不允许为了通过校验改变已有评价结论。

`generate_teaching.md` 的调整：

1. 输出字段缩减为 `content`、`questions`。
2. 删除原因组及验证方式表、原因选择与证据约束、诊断与验证约束（已迁移到阶段一）；`main_reason`、`other_reasons`、`judge_reason` 以 `latestEvaluation` 中的已确认值为唯一来源，只能使用，不能重算、重排或覆盖。
3. 只执行 `instructionFromRules.allowedAction`；缺少该字段时视为后端调用错误，不自行推断动作。
4. 保留防泄露、避免重复、问题数量约束，以及各动作的教学重点执行要求（如 `GIVE_HINT` 给推动当前步骤的最小提示、`GIVE_CORRECTION` 修正已确认的局部错误等）。

完成本步后先做提示词契约检查，确认原因分类和评价字段只由阶段一负责，阶段二只负责按已确认原因组织内容，再进入后端改造。

### 第二步：拆分 Schema 和确定性规则

修改文件：

- `backend/app/schemas/ai_evaluation.py`
- `backend/app/schemas/teaching.py`
- `backend/app/schemas/merged.py`（迁移完成后删除）
- `backend/app/rules/teaching_decision.py`

具体调整：

1. 在 `ai_evaluation.py` 增加阶段一输出类型，字段为现有评价字段（`correctness`、`completeness`、`coveredPoints`）加 `has_progress`、三项原因字段；不再接受 `errorEvidence` 和教学字段，多余字段由 Schema 拒绝；动态 `coveredPoints` 枚举校验继续复用现有实现。
2. 在 `teaching.py` 定义阶段二的 `TeachingOutput` 与 `TeachingQuestion`，并按 `allowedAction` 校验问题数量。
3. `decide_teaching()` 改为接收阶段一输出，不再读取模型给出的 `teachingAction`、`content` 或 `questions`。函数只返回状态变化、计数结果和 `allowed_action`。
4. 保留完成状态、覆盖点、无进展计数、支持上限和非评分点评价模式的现有确定性逻辑。
5. 所有引用迁移后删除 `merged.py`，避免合并契约和拆分契约同时存在。

这一阶段不新增数据库字段。`main_reason` 等字段保存在阶段一原始响应和请求审计中，并以内存中的类型化结果传给阶段二。若以后需要按原因做数据库查询，再单独设计迁移；本轮先避免扩大数据模型范围。

### 第三步：接入两次调用

新增文件：

- `backend/app/services/ai_teaching.py`

修改文件：

- `backend/app/services/ai_evaluation.py`
- `backend/app/api/sessions.py`
- `backend/app/repositories/sessions.py`

具体调整：

1. `AIEvaluationService.evaluate()` 只渲染阶段一 Schema，解析阶段一输出并保存 `AIEvaluation`。传输失败和 Schema 失败继续沿用现有重试与人工处理路径。
2. 新增 `AITeachingService.generate()`，渲染 `generate_teaching.md`，传入阶段一结果和 `allowedAction`，并独立记录 `AI_TEACHING` 请求、响应、耗时和校验结果。
3. `submit_text_attempt()` 调整为“评价 → 决策 → 按需生成教学 → 落库”。完成态和支持上限在第二次模型调用前结束，节省不必要的请求。
4. `SessionRepository.apply_teaching_decision()` 改用 `TeachingQuestion`，仍由它统一创建 `SupportEvent`、更新计数和推进 `flow_stage`。
5. 阶段二传输或结构重试耗尽时，关联已有 `evaluation_id` 进入人工处理；不得再次调用阶段一，也不得生成第二条评价记录。

前端 API 响应、`SupportEvent` 展示方式和现有会话版本控制不变。

### 第四步：验证拆分边界

新增测试文件：

- `ljg_docs/10-自讲请求拆分/test_split_explanation_requests.py`

至少覆盖以下场景：

1. 阶段一 Schema 拒绝教学字段和 `errorEvidence`，阶段二 Schema 拒绝评价和原因字段。
2. `CORRECT + COMPLETE` 直接完成，且没有 `AI_TEACHING` 调用。
3. 无进展固定选择 `GIVE_HINT`；有进展且错误选择 `GIVE_CORRECTION`；有进展、正确但不完整选择 `ASK_FOCUSED_QUESTION`。
4. 支持上限在阶段二之前拦截，不产生教学请求。
5. 阶段一成功、阶段二首次失败时只重试阶段二，评价调用次数保持一次。
6. 阶段二重试耗尽后保留评价记录，并进入人工处理路径。
7. 阶段二问题数量与 `allowedAction` 不匹配时触发结构重试。
8. 最终 `SessionResponse`、计数和 `flow_stage` 与拆分前的公开接口保持兼容。

完成测试后执行：

```powershell
pytest -q ljg_docs/10-自讲请求拆分/test_split_explanation_requests.py
pytest -q backend/tests/unit backend/tests/integration/test_teaching_cycle.py
git status --short
git diff -- backend/app ljg_docs/10-自讲请求拆分
```

## 验收标准

- 一次自讲最多产生一次有效评价；阶段二重试不重复阶段一。
- 阶段一不返回教学内容，阶段二不返回评价、原因或动作字段。
- 阶段一不再输出 `errorEvidence`，错误依据统一由 `judge_reason` 承载；原因分类只由阶段一产出，阶段二不重算。
- 状态转换、支持计数、阈值和 `allowedAction` 全部由后端确定。
- 完成态和支持上限不会调用阶段二。
- 两阶段请求分别留下可检索的审计记录和耗时。
- 前端接口无需调整，现有自讲、追问、提示和纠错交互保持可用。

## 合理性批判与不足

1. 两次调用会增加非终态请求的延迟和 Token 成本。现有实验中，实验二平均约 13.2 秒、每个样本约 7370 Token；收益主要是职责隔离、独立重试和可审计性。建议上线后分别统计 `AI_EVALUATION` 与 `AI_TEACHING` 的 P50、P95、输入 Token 和重试率，确认质量收益是否抵得上成本。
2. 原因字段暂不拆成数据库列，查询和报表只能读取审计响应。这样能避免本轮引入迁移，但如果近期要做错因统计，这个方案不够用，届时应先定义原因字段的保存周期和用途。
3. 当前动作表按 `hasProgress=false`、`WRONG`、`INCOMPLETE` 的顺序匹配，无法表达“先纠错再追问”。这是有意保留的简化规则。若真实样本经常需要 `CORRECT_AND_ASK`，应单独评估动作表，不能靠阶段二自行扩展。
4. 当前工作区在相关后端文件上已有未提交改动。实施时必须以当时工作区为基线逐文件检查，避免覆盖现有修改；提交时只暂存本方案实际改动的代码文件。
5. 移除 `errorEvidence` 后，错误依据只剩 `judge_reason` 自由文本，程序化定位具体错误文本的能力下降。若后续要做错因统计或错误定位，需要约定 `judge_reason` 中引用原文的格式，或重新引入结构化字段；本轮先以“引用原话时逐字摘自 `confirmedText`”作为软约束。
6. 原因分类整体迁到阶段一后，阶段二无法在组织内容时调整原因或补充验证，分类错误会直接传导到教学内容。阶段一质量成为整条链路的关键瓶颈，需要单独评估阶段一提示词的稳定性和复现率。
