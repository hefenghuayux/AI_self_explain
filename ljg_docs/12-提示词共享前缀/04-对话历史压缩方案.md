# 对话历史压缩方案

## 1. 结论

本方案只压缩对话历史。system prompt、题目材料、任务指令、输出 Schema、规则状态、当前输入和本次临时引导例子都不参加压缩。

压缩采用一套简单规则：

1. 业务模型调用成功后，读取 DeepSeek 返回的 `usage.total_tokens`。达到模型上下文窗口的 80% 时，在当前业务请求全部结束后，为该会话启动异步压缩。
2. 新消息到达时，先估算即将发送的完整请求。预计达到上下文窗口的 90% 时，暂存这条消息，先完成压缩，再继续处理。
3. 如果 DeepSeek 最终仍返回上下文溢出错误，强制压缩一次，然后重试原请求一次。
4. 压缩时保留最近约 1/3 的原始历史，至少保留 2 个完整交互组。更早的约 2/3 由一次独立的模型请求总结。
5. 摘要替换被裁剪历史，原始数据库记录不删除。

这里的“独立模型请求”是一次普通的 DeepSeek 调用，不启动带工具和独立生命周期的完整子 Agent。

## 2. 设计原则

### 2.1 复用现有结构

本方案不增加历史表、摘要表、队列表，也不增加 `TeachingCycle` 一类新的业务模型。

直接复用现有能力：

- 历史来源继续使用 `ExplanationAttempt`、`SupportEvent` 和事件序方案生成的 `events`；
- 历史分组继续使用《事件序进展上下文改造方案》中的完整交互组；
- 摘要写入现有 `session_events`，事件类型仍为 `context.added`，`kind` 使用已有的 `memory`；
- 模型可见历史仍放在共享前缀方案的 `messages[2]`；
- 压缩期间的等待只使用进程内的会话级锁和 FIFO 队列。

运行时需要少量协调状态，但不持久化新的业务数据结构。服务重启时，正在等待的 HTTP 请求会失败，由前端保留输入并让用户重试；已经写入 `session_events` 的摘要不会丢失。

### 2.2 依赖统一的共享历史

本方案建立在《共享前缀对照草案》的五层消息结构上：

```text
messages[0] system：全局 system prompt
messages[1] user：题目等稳定上下文
messages[2] user：共享对话历史
messages[3] user：taskType 指令和输出 Schema
messages[4] user：本轮动态数据
```

压缩只改写 `messages[2]` 的模型视图。评价、教学生成、疑问支持和子问题复核应读取同一份共享历史投影，避免每个 taskType 分别生成一份互不一致的摘要。

## 3. 不可压缩内容

以下内容始终完整保留：

- system prompt；
- 题目、标准答案、评分点、常见错误和完整解答；
- taskType 固定指令；
- JSON Schema 和字段约束；
- 业务状态、次数、阈值和规则动作；
- 当前学生输入；
- 当前评价结果；
- 本次原因对应的临时引导例子；
- Schema 重试需要的错误和上次输出。

原因引导例子只服务于本次教学生成。下一次原因变化时直接替换，不进入对话历史，也不进入摘要。

## 4. 压缩触发规则

DeepSeek‑V4.1‑Flash 当前官方上下文长度为 1M token。本项目不追求使用完整容量，按自讲场景设置较短的有效上下文窗口，让历史更快进入“最近内容优先”的状态，也减少无关远期内容对当前评价的干扰。

建议初始配置：

| 配置项 | 初值 | 用途 |
| --- | ---: | --- |
| `ai_context_window_tokens` | 258000 | 本项目采用的有效上下文窗口 |
| `context_compaction_after_response_ratio` | 0.80 | 成功响应后的异步压缩阈值 |
| `context_compaction_before_request_ratio` | 0.90 | 新请求发送前的同步等待阈值 |
| `ai_max_output_tokens` | 10000 | 业务请求输出预留和请求上限 |
| `context_compaction_summary_max_tokens` | 1024 | 摘要请求最大输出 |
| `context_compaction_wait_timeout_seconds` | 与 AI 请求超时相同或略高 | 排队请求最长等待时间 |

### 4.1 成功响应后的 80% 触发

每次业务模型调用最终成功后，读取 DeepSeek 返回的：

```text
usage.total_tokens
```

满足以下条件时，将当前会话标记为需要压缩：

```text
usage.total_tokens >= ai_context_window_tokens × 0.80
```

一次学生提交可能先调用评价模型，再调用教学模型。中间调用达到 80% 时只记录压缩需求，必须等本次业务请求中的模型调用、状态更新和数据库提交全部完成后，再启动后台压缩。不能让压缩和同一业务请求中的下一次模型调用同时读取、改写历史视图。

业务响应先返回给用户，压缩在后台进行。压缩期间，同一会话的新请求进入 FIFO 等待；其他会话不受影响。

`usage.total_tokens` 包含本次输入和输出，因此它是偏保守的压力指标，可能比只看输入更早触发。这个误差方向可以接受。压缩请求自身不参与 80% 检查；Schema 重试只在该业务调用最终成功后检查一次。

### 4.2 新消息到达后的 90% 预检

收到新消息后，在写入业务状态和调用模型前，先构造预计发送的最终消息，并计算：

```text
estimated_input_tokens + ai_max_output_tokens
```

满足以下条件时，当前消息暂存在会话 FIFO 中：

```text
estimated_input_tokens + 10000
    >= ai_context_window_tokens × 0.90
```

如果会话没有正在压缩，则立即启动压缩；如果已经在压缩，则等待同一个任务。摘要写入成功后，请求按到达顺序继续处理。

暂存不提前推进业务状态。请求出队时重新读取会话，执行现有流程阶段和 `version` 校验。排队期间版本已经变化的请求返回现有的 `409 SESSION_VERSION_CONFLICT`，不能自动改用新版本重放。

第一版保持现有同步 HTTP 接口：请求连接等待压缩完成，之后仍返回原来的 `SessionResponse`。等待超时返回：

```text
503 CONTEXT_COMPACTION_TIMEOUT
```

此时消息没有进入业务状态，前端保留用户输入并允许重试。

### 4.3 上下文溢出后的强制恢复

如果 DeepSeek 明确返回上下文窗口溢出错误：

1. 跳过 80% 和 90% 判断；
2. 对当前会话强制执行一次历史压缩；
3. 使用压缩后的历史重建原请求；
4. 重试原请求一次。

第二次仍然溢出时，返回明确错误，不继续循环压缩：

```text
CONTEXT_WINDOW_EXCEEDED_AFTER_COMPACTION
```

强制恢复仍只能处理对话历史。不可压缩内容或当前单条输入本身过长时，保留错误，不静默截断。

## 5. token 计量

### 5.1 实际值

80% 触发以 DeepSeek 响应中的 `usage.total_tokens` 为准。现有事件记录需要补充保存 `total_tokens`，不能用 `prompt_tokens + completion_tokens` 的本地推导替代服务端值。

### 5.2 请求前估算

90% 预检和历史裁剪使用项目内已有的 DeepSeek V4 tokenizer：

```text
scripts/deepseek_v4_tokenizer/deepseek_v4_tokenizer/tokenizer.json
```

实现时增加轻量的 `tokenizers` 依赖，直接加载 `tokenizer.json`。不引入完整的 `transformers`。tokenizer 在应用启动时加载一次，后续复用。

`tokenizers` 不负责执行 `tokenizer_config.json` 中的 Jinja chat template，因此需要按该模板实现一个很小的消息序列化函数。当前业务请求只有 `system` 和连续 `user` 消息，序列化器只支持这两类角色和结尾的 assistant 生成标记；遇到未支持的角色直接报错。计数对象是序列化后的完整请求，不能只统计各字段正文。角色标记、JSON 字段名、分隔符和模板字符都占 token。

随 tokenizer 提供的 `tokenizer_config.json` 中，`model_max_length=16384` 是旧配置元数据，不作为当前模型容量。当前 `deepseek-flash` 的官方容量为 1M，但本项目的阈值和预检统一按配置的 258K 有效窗口计算。

tokenizer 文件缺失或加载失败时，应用启动直接报错，不退回字符估算。字符比例只适合人工估算，不能控制压缩阈值。

## 6. 历史裁剪规则

### 6.1 裁剪单位

“至少保留 2 条消息”在本项目中解释为至少保留 2 个完整交互组。原因是共享历史在 Chat API 中整体位于一条 `messages[2]`，直接按 Chat message 数无法裁剪内部历史。

完整交互组直接复用事件序方案：

| 类型 | 组成 |
| --- | --- |
| 完整引导问答 | `teaching → guided_answer → follow_up`，或没有跟进的前两项 |
| 自讲后直接教学 | `explanation → teaching` |
| 孤立自讲 | 单独的 `explanation` |

不得从中间截断学生文本，也不能留下“只有答案没有问题”或“只有反馈没有回答”的残缺历史。

### 6.2 保留最近 1/3

以压缩前模型可见历史的 token 数为基准：

```text
retain_budget = floor(history_tokens / 3)
```

从最新交互组向前累加：

1. 先保留最近 2 个完整交互组；
2. 继续尝试加入更早的完整交互组；
3. 如果加入下一组会超过 `retain_budget`，该组不保留；
4. 因完整组边界而无法刚好达到 1/3 时，允许多裁掉一组，使保留原文低于 1/3；
5. 最近 2 组优先，因此它们合计超过 1/3 时允许超出保留预算。

被移除的旧历史是本次摘要源。最近保留的原始历史不进入摘要，避免摘要和原文重复。

压缩后的模型可见历史由“摘要 + 最近约 1/3 原文”组成，因此最终长度会略高于原历史的 1/3。1/3 只约束原文保留量，不包含摘要。

历史不足 2 个完整交互组，或没有能够安全移除的组时，本次压缩返回 `no-op` 并记录原因。不能为了完成压缩拆开交互组。

## 7. 摘要请求

### 7.1 请求方式

摘要使用同一个 `deepseek-flash`，关闭思考模式，输出上限为：

```text
min(1024, 被总结历史 token 数 / 4)
```

请求复用原 system、稳定题目上下文和压缩前历史，在最后追加压缩指令。指令明确给出需要总结的交互组或 `interactionId` 范围，只允许总结被移除的旧历史。这样可以复用请求前部的 DeepSeek 前缀缓存，也不会把当前任务指令、当前输入或临时例子写进摘要。

压缩提示词参考 DeepSeek Harness 的做法：固定结构、简短条目、保留准确引用、合并旧摘要、禁止执行其他任务。内容改成适合教学会话的版本。

### 7.2 压缩提示词草案

```text
你现在只负责压缩上方对话历史中指定的旧交互组范围。

目标：生成一份简短、准确的历史摘要，让后续评价和教学能够继续；不要评价当前输入，不要决定业务状态，不要生成新的教学内容。

只总结指定的 `interactionId` 范围：{{SOURCE_START_INTERACTION}} 到 {{SOURCE_END_INTERACTION}}。
最近保留的原始事件不进入摘要。

严格使用以下 Markdown 结构。没有内容时写“无”，不得省略标题。

## 学生已表达的理解
- 保留学生实际说过的推理、结论和关键短引用。

## 已进行的教学与学生回应
- 记录已经给出的提示、问题以及学生实际回答。

## 已确认的问题与证据
- 记录已有评价明确指出的问题及其依据，不自行增加判断。

## 尚未解决的问题
- 只记录历史中仍未解决的疑问或错误。

规则：
- 只输出摘要正文。
- 内容必须来自指定历史，不能补充常识或推断学生已经掌握。
- 保留题目中的数字、公式、术语和必要的学生原话。
- 不记录 system prompt、任务指令、JSON Schema、状态、计数、阈值或下一步业务动作。
- 如果历史中已有压缩摘要，将其中仍然有效的信息与本次旧历史合并为一个新摘要，不要原样复制旧摘要。
```

### 7.3 摘要校验

摘要必须满足：

- 返回非空纯文本；
- 未因输出上限被截断；
- 摘要 token 数严格小于被替换历史；
- 压缩期间选定的来源范围没有变化。

任一条件不满足时，本次压缩失败，原模型视图保持不变，并记录明确错误。这里不增加复杂修复逻辑。

## 8. 摘要写入和历史重建

### 8.1 写入现有事件

摘要使用现有事件类型：

```json
{
  "eventType": "context.added",
  "data": {
    "kind": "memory",
    "source": "context_compaction",
    "content": {
      "version": 1,
      "summary": "...",
      "sourceStartInteractionId": "attempt:12",
      "sourceEndInteractionId": "support:48:followup",
      "sourceTokens": 12000,
      "summaryTokens": 900
    }
  }
}
```

这些字段存放在已有 JSON `content` 中，不新增数据库列。

### 8.2 模型可见历史

历史构造器读取最新的压缩记忆：

```text
压缩摘要
→ sourceEndInteractionId 之后未被覆盖的原始交互组
```

被摘要覆盖的原始事件继续保存在数据库和轨迹中，但不再进入业务模型请求。

再次压缩时，把“旧摘要 + 本次新移除的旧历史”合并成一个新摘要。模型可见历史中始终只有一个有效摘要，不能累积多段摘要。

写入前再次确认来源交互组和 `interactionId` 没有变化。发现变化时丢弃本次结果并记录错误，不能覆盖更新后的历史。若历史来自 `session_events` 且已有持久化 `seq`，可以同时记录起止 `seq` 作为审计信息；不能把 `progressContext.events[].seq` 这种临时序号当成持久化边界。

## 9. 会话级单飞和消息暂存

每个会话同一时间最多运行一个压缩任务。

运行顺序如下：

```text
当前业务请求完成
→ 达到 80%，启动后台压缩
→ 新请求到达，进入该会话 FIFO
→ 摘要生成并写入
→ 释放会话锁
→ 按到达顺序继续处理等待请求
```

90% 预检和上下文溢出恢复复用同一把会话锁。多个请求不能重复启动摘要调用。

后台压缩需要创建自己的数据库会话，不能复用已经结束的 HTTP 请求数据库会话。

同一历史版本压缩失败后，不在每个后续 80% 检查中反复尝试。历史新增，或进入 90%、上下文溢出路径时，才允许再次压缩。

## 10. DeepSeek Harness 的继承与简化

本方案继承以下做法：

- 上下文达到 80% 后自动触发；
- system prompt 不进入被替换范围；
- 保留最近原始历史，总结更早历史；
- 使用单独的辅助模型请求；
- 旧摘要在下一次压缩时合并；
- 摘要不比源历史短时拒绝提交；
- 压缩期间，同一会话的新消息等待；
- 溢出后允许压缩并重试。

本项目不复制 Harness 的 surface 事务、工具结果裁剪、多 provider 路由、手动 `/compact` 命令和多次压缩重试。教学会话触发压缩的概率较低，第一版保留一条清楚的成功路径和必要错误即可。

## 11. 执行链路

### 11.1 正常后台压缩

1. 业务模型成功返回。
2. 保存原始 `usage.total_tokens`。
3. 当前业务请求全部完成后判断是否达到 80%。
4. 达到阈值则返回业务响应，并启动后台压缩。
5. 按完整交互组切分最近 1/3 与旧 2/3。
6. 模型总结旧历史。
7. 校验摘要并写入 `context.added(kind=memory)`。
8. 后续请求使用“一个摘要 + 最近原始历史”。

### 11.2 90% 请求前压缩

1. 新消息到达。
2. tokenizer 估算完整输入，并加 10K 输出预留。
3. 达到 90% 时暂存请求并获取会话压缩锁。
4. 压缩成功后重新读取会话并校验版本。
5. 使用新历史处理原消息。

### 11.3 溢出恢复

1. DeepSeek 返回上下文溢出。
2. 强制压缩一次。
3. 重建并重试原请求一次。
4. 再次溢出则返回明确错误。

## 12. 验收标准

至少验证以下行为：

1. `usage.total_tokens` 达到 80% 后，压缩在完整业务请求结束后启动。
2. 未达到 80% 时不启动后台压缩。
3. 90% 预检包含最终消息和 10K 输出预留。
4. 压缩只裁剪共享历史，其他消息内容逐字不变。
5. 保留最近约 1/3，且至少保留 2 个完整交互组。
6. 不拆分问题、回答、反馈或单条学生文本。
7. 被移除历史由单独模型请求总结，摘要关闭思考模式。
8. 压缩摘要写入已有 `context.added(kind=memory)`。
9. 原始历史仍可查询，但不再进入模型可见历史。
10. 第二次压缩合并旧摘要，模型视图只有一个摘要。
11. 压缩期间的请求按会话 FIFO 等待，其他会话正常处理。
12. 等待请求出队后重新执行版本和流程阶段校验。
13. 上下文溢出只强制压缩并重试一次。
14. 摘要失败、等待超时和重试后仍溢出都有明确错误。

## 13. 实施范围

本轮只修改设计文档。后续实现预计涉及：

- `backend/app/core/config.py`：增加上下文容量、阈值、输出上限和等待超时配置；
- `backend/app/services/session_event_log.py`：记录 `usage.total_tokens`，复用 `context.added` 写入摘要；
- 共享历史构造逻辑：读取最新摘要并跳过已覆盖的原始事件；
- AI 调用公共入口：接入 80%、90% 和溢出重试；
- 应用级协调器：维护进程内的会话单飞锁和 FIFO；
- `backend/pyproject.toml`：增加 `tokenizers`；
- 评价、教学和支持服务：统一使用压缩后的 `messages[2]`。

实现前需要先完成或同步完成共享历史统一，否则不同 taskType 会看到不同的压缩边界。

## 14. 合理性批判与不足

1. **`usage.total_tokens` 会提前触发。** 它包含输出 token，不能精确表示下一次输入压力。方案接受这个偏差，因为压缩很少触发，提前一些比越过窗口安全。
2. **摘要可能损失学生措辞。** 提示词要求保留关键短引用，但模型仍可能弱化细节。最近 1/3 保留原文可以减轻问题，无法完全消除。
3. **进程内队列只适合当前单进程部署。** 多 worker 或多实例部署时，同一会话可能进入不同进程，需要数据库锁或外部队列。本阶段不提前增加这套复杂度。
4. **10K 输出上限仍需校准。** 当前业务 JSON 通常不会达到 10K，但推理模型的输出分布仍需通过真实 `completion_tokens` 观测确认；如果频繁触顶，再单独调整。
5. **统一共享历史是前置条件。** 当前评价和教学生成仍有各自的历史来源。如果没有先统一 `messages[2]`，单一摘要无法稳定服务所有 taskType。
