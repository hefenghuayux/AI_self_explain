# 提示词共享前缀实施前决策稿

编写日期：2026-09-17

## 一、结论

这项改造值得做，但目标需要说清楚：它不是“启用 DeepSeek 缓存”。DeepSeek 的上下文硬盘缓存已经默认开启，当前单条 `user` 消息也可能命中缓存。改造的价值在于重新排列请求内容，让更多稳定内容处在变化点之前，从而扩大可复用前缀，并让真实请求结构更容易审计。

本阶段采用以下方案：

1. 把请求拆成全局 system、会话级稳定上下文、共享历史、taskType 固定指令、本轮任务数据五层。
2. 题目材料和共享历史放在 taskType 之前；本轮输入、任务专属数据和一次性内容放在最后一层。
3. 保留四个 taskType 的独立模板，不合并为一个多任务提示词。
4. 原因引导例子只进入本轮 `generate_teaching` 的动态尾部，下一轮不再发送。
5. 请求结构使用 DeepSeek 原生消息角色和真实顺序，但不复制 DeepSeek Harness 的完整 Agent 会话、工具和压缩架构。
6. 先从已有 `raw_response` 统计缓存基线，再分阶段改造并比较命中、结构重试和输出一致性。

本文件是实施前决策稿。本轮只修正文档，不修改后端代码。

## 二、当前基线

当前四类模型任务都把静态指令、JSON Schema、题目材料、历史和本轮输入渲染进一条 `user` 消息：

```text
messages[0] user
  taskType 固定指令
  原因定义与字段规则
  JSON Schema
  题目材料
  必要历史
  本轮输入
  结构重试信息
```

代码现状如下：

- `ModelRequestMessage.role` 只允许 `"user"`。
- `ai_evaluation.py`、`ai_teaching.py` 和 `ai_support.py` 都发送一条 user 消息。
- `ModelTransportSnapshot.messages` 已能保存消息数组，无需再增加平行的 `system_message` 字段。
- 模型原始响应保存在 `external_call_records.raw_response`，其中可离线读取 DeepSeek 的 usage 数据。

现状并不等于“完全无法缓存”。同一个 taskType 的模板头部如果保持一致，仍可能形成公共前缀。主要问题有两个：

- 跨 taskType 的共同内容复用较弱，因为任务身份和各自模板从开头就不同。
- 静态内容与动态内容的边界不清楚，题目、历史或重试信息一旦变化，变化点之后的内容无法延续原前缀。

## 三、DeepSeek V4.1 的缓存规则

当前使用的 `deepseek-flash` 对应 DeepSeek‑V4.1‑Flash，支持上下文硬盘缓存。官方文档说明该能力默认开启，调用方不需要发送单独的 cache 开关。

缓存判断基于模型实际收到的完整前缀。系统会在用户输入结束、模型输出结束、检测到公共前缀以及长内容的固定 token 间隔处生成缓存前缀单元。后续请求只有完整匹配已经落盘的前缀单元时才会命中。缓存构建属于尽力而为，通常需要秒级时间；长时间未使用的缓存一般在数小时到数天后清理。

因此需要遵守三条原则：

1. 稳定内容尽量靠前，变化内容尽量靠后。
2. 请求开头的内容、消息角色和排列顺序要稳定，JSON 序列化顺序也要确定。
3. 不把命中视为必然结果。两个请求有共同字符串，不代表公共部分已经被单独落盘。

DeepSeek 返回的缓存字段是：

- `usage.prompt_cache_hit_tokens`
- `usage.prompt_cache_miss_tokens`

不存在本草案旧版所写的 `X-Cache-TTL` 和 `usage.prompt_cached_tokens`。

截至 2026-09-17，`deepseek-flash` 的官方价格为：

| 项目                       | 空闲时段 | 高峰时段 |
| -------------------------- | -------: | -------: |
| 百万输入 token，缓存命中   |   ¥0.02 |   ¥0.04 |
| 百万输入 token，缓存未命中 |      ¥1 |      ¥2 |
| 百万输出 token             |      ¥4 |      ¥8 |

价格会调整，实施和复盘时应以官方页面为准。

## 四、设计目标与非目标

### 4.1 设计目标

- 增加同题目、同会话内四个 taskType 之间可复用的前缀。
- 保持评价、教学、疑问支持和子问题评估的职责隔离。
- 让审计快照能够还原真正发送给模型的消息顺序。
- 明确一次性原因例子的生命周期，避免旧例子污染下一轮判断。
- 用现有数据建立基线，改造后可以判断成本和行为是否真的改善。

### 4.2 本阶段不做

- 不实现完整的 `model_view` 投影层。
- 不做历史摘要、microcompact、context collapse 或多级缓存断点。
- 不引入 Claude Code 式供应商专用 cache editing。
- 不为了缓存命中保留已经失效的一次性教学例子。
- 不合并四个任务，也不改动确定性状态机、计数或阈值规则。

## 五、推荐消息结构

单次请求固定按以下顺序发送：

```text
messages[0] system：全局共享前缀
messages[1] user：会话级稳定上下文
messages[2] user：截至当前任务前的共享历史
messages[3] user：taskType 固定指令 + JSON Schema
messages[4] user：本轮任务数据
```

### 5.1 `messages[0]`：全局共享 system

只放四个任务都需要、且不随题目和轮次变化的规则：

- AI 自讲 Demo 的全局角色边界。
- 状态、计数和阈值由确定性代码控制。
- 按后续任务给出的 JSON Schema 返回单个 JSON 对象。
- 五类原因的名称、定义和通用诊断原则。
- 原因是本轮诊断假设，不能作为学生长期标签。

字段关系、终态规则、重试规则以及 taskType 特有行为不放在共享 system 中。

共享 system 可以从统一模板加载。它的渲染结果和段落顺序必须稳定，不包含当前题目、学生文本、状态值、时间、请求 id、当前原因或例子。

### 5.2 `messages[1]`：会话级稳定上下文

这一层放同一教学会话内保持不变、并且四个 taskType 都会使用的内容，例如：

- 题干和题目基础材料。
- 学习目标或评分材料中确实全任务公用的部分。
- 题目版本等稳定标识。

这层应使用固定字段顺序和确定性的 JSON 序列化。可选字段不能一轮省略、下一轮又以 `null` 补回。

共享历史不与题目材料混在这一层。题目上下文保持不变；历史随对话增长，两者需要分别构造和审计。

如果某项题目材料只服务于一个任务，应留在该任务指令或动态上下文中。为了共享缓存而给所有任务重复发送无用长文本，可能得不偿失。

### 5.3 `messages[2]`：共享历史

这一层放当前任务开始前，四个 taskType 都能读取的完整对话历史。现阶段对话通常不超过 10 轮，可以先全量保留，不做摘要或压缩。

共享历史必须有明确截止点。评价和紧随其后的教学生成如果基于同一轮学生输入，应尽量从同一历史快照开始；评价结果、规则动作等后产生的数据放到各自的本轮任务数据中。这样切换 taskType 时，请求仍能共享 system、题目材料和历史前缀。

历史按固定格式和原始顺序序列化，已经保存的旧条目不回写。内容需要明确标注为历史证据，不能被模型当成当前指令。以下内容不进入共享历史：

- 当前任务尚未处理的学生输入。
- 最新评价结果或本轮规则动作。
- 一次性原因引导例子。
- 上一轮模型草稿、校验错误和重试说明。

这种排列有一个取舍：历史增长后，位于它后面的 taskType 模板需要重新计算；同一历史快照切换任务时，却可以复用整段历史。当前流程经常连续调用评价和教学生成，且任务模板远短于多轮历史，因此优先保留跨任务的历史前缀。

### 5.4 `messages[3]`：taskType 固定指令

每个 taskType 继续使用独立模板。本层包含：

- 任务身份与职责。
- 输入字段的解释。
- 输出字段关系。
- 当前任务的终态或动作规则。
- 结构重试规则。
- JSON Schema。

四个任务的边界如下：

| taskType                  | 固定模板负责的内容                                             |
| ------------------------- | -------------------------------------------------------------- |
| `evaluate_explanation`  | 正确性、完整性、评分点、进展和原因判断；不生成教学内容         |
| `generate_teaching`     | 使用既定评价和规则动作生成教学内容；不重新评价、改原因或改状态 |
| `generate_support`      | 回应当前疑问，选择规定的支持动作；不判断学习进展               |
| `assess_guided_answers` | 逐题评估子问题作答并生成整合引导；不改业务状态                 |

模板内容和 JSON Schema 在同一版本内保持稳定。修改任一模板都应提升 `promptVersion`，便于将缓存和行为变化关联到具体版本。

任务指令放在历史之后还有一个直接收益：taskType、字段关系和 JSON Schema 更靠近本轮输入及模型输出。历史较长时，这个位置比放在历史前更利于模型遵循当前任务。

### 5.5 `messages[4]`：本轮任务数据

这一层按固定小节顺序组织：

1. 本轮学生输入。
2. 当前任务专属的上下文，例如最新评价或规则层已确定的动作。
3. 当前原因对应的一次性引导例子，仅 `generate_teaching` 使用。
4. 上一轮原始输出和结构校验错误，仅重试时使用。

字段缺失时使用统一的省略规则，不要在空字符串、空数组、`null` 和整段删除之间随机切换。稳定的渲染方式有利于调试，也能减少无意义的前缀差异。

### 5.6 为什么允许连续四条 user 消息

DeepSeek 的 OpenAI 兼容 Chat Completions 接口支持按顺序传入消息。DeepSeek Harness 的适配器同样保留 system、user、assistant 和 tool 的真实顺序，不会把所有内容强行拼成一条 user 消息。

这里借鉴的是它的消息建模原则：

- 使用供应商原生角色。
- system 位于最前。
- 模型看到什么，审计快照就保存什么。
- 共享历史按发生顺序排列，当前任务数据留在尾部。
- 没有值的可选请求字段直接省略，不发送 `null`。

当前项目没有 Agent 工具循环，也不需要照搬 DeepSeek Harness 的事件 surface、工具消息转换或压缩事务。实现前仍应增加一条集成测试，确认项目实际使用的 DeepSeek 端点或代理不会合并、拒绝连续 user 消息。

## 六、最小共享 system 草案

下面的文字用于界定共享范围，实施时仍需与四个现有模板逐句去重。

```markdown
你是 AI 自讲 Demo 的后端模型组件。后续消息会给出本轮任务、题目上下文和动态输入。只执行本轮任务定义的职责。

## 全局边界

- 业务状态、计数和阈值由后端确定性代码控制。只能使用已提供的值，不能修改、补算或覆盖。
- 按本轮任务给出的 JSON Schema 返回一个 JSON 对象，不输出 Markdown、解释文字或 Schema 之外的字段。
- 不自行切换任务类型，不执行本轮任务未授权的评价、教学或状态决策。

## 原因定义

- 表达与输入问题：表达遗漏、过于简略或含义不清，现有文本可能没有准确反映学生原意。
- 题意理解问题：误解或遗漏题目条件，不清楚对象或所求。
- 知识理解与回忆问题：不知道、想不起或误解相关概念、公式或规则。
- 知识应用问题：知道相关知识，但不会结合本题使用，或无法说明当前推理依据。
- 执行错误：思路和依据基本正确，但计算、抄写、代入或符号操作出错。

原因只表示本轮可修正的诊断假设，不是学生的长期标签。不得把原因标签写进学生可见内容。单纯请求完整答案不能证明存在知识缺陷。
```

以下规则留在任务模板中：

- `mainReason`、`otherReasons`、`judgeReason` 的字段关系。
- `CORRECT + COMPLETE` 或全部答对时的空原因规则。
- `ASK_FOCUSED_QUESTION`、`GIVE_HINT`、`GIVE_CORRECTION` 等动作约束。
- 输出长度、问题数量、字段命名以及结构重试要求。

## 七、一次性原因引导例子

### 7.1 数据契约

在 `TeachingContext` 增加：

```json
{
  "reasonGuidanceExamples": [
    {
      "reason": "知识应用问题",
      "example": "……"
    }
  ]
}
```

约束如下：

- 由后端根据 `latestEvaluation.mainReason` 确定性选择。
- 数组可以包含多条例子，但每条 `reason` 都必须等于当前 `mainReason`。
- 例子只用于参考引导方式，提示词中明确禁止照抄。
- 该字段只进入 `generate_teaching`，不进入评价、疑问支持或子问题评估请求。

### 7.2 生命周期

第 N 轮原因为 A 时，请求尾部可以包含 A 的例子。第 N+1 轮原因为 B 时，重新构造动态上下文，只包含 B 的例子，A 不再出现在模型可见请求中。

这种替换会让 A/B 变化点之后的后缀重新计算。全局 system、题目上下文、共享历史以及同一 taskType 的固定模板仍有机会命中。不能为了保住一小段尾部缓存，把已经失效的 A 继续留给模型。

评价器不需要看到例子本身。它仍然可以通过教学历史看到实际发给学生的教学内容，据此判断学生后续回答是否只是复述提示，以及是否产生了真实进展。

## 八、审计快照与传输契约

### 8.1 消息角色

不在 `ModelTransportSnapshot` 增加 `system_message`。已有 `messages` 就是真实传输结构，只需扩展：

```python
class ModelRequestMessage(BaseModel):
    role: Literal["system", "user"]
    content: str
```

当前四类任务不需要伪造 assistant 历史。以后只有在模型确实需要看到原始 assistant 消息时，才评估是否扩展角色集合。

### 8.2 blocks

`ModelRequestBlocks` 调整为能够区分共享 system 和任务指令：

- `systemInstructions`：共享 system 的渲染结果。
- `questionContext`：会话级稳定题目上下文。
- `sessionContext`：截至当前任务前的共享历史及其截止点。
- `taskInstructions`：当前 taskType 的固定指令和 Schema。
- `memoryContext`、`userInput`、`retryContext`：继续保存各自事实。

`transport.messages` 保存真实发送顺序，是还原模型输入的最终依据。blocks 用于结构化审计，不能与 transport 形成另一套含义不同的“近似请求”。

### 8.3 Schema 版本

- 新快照使用 `schemaVersion: "1.1"`。
- 已保存的 `1.0` 记录继续按旧结构读取，不批量改写历史数据。
- 读取层根据版本解析；写入层只生成 `1.1`。
- 轨迹和调试页面按 `transport.messages` 展示多条消息，并显示角色和顺序。

## 九、基线与收益计算

先离线解析 `external_call_records.raw_response`，不在本阶段新增数据库字段或监控表。

基线至少按 `taskType`、模型名和 `promptVersion` 汇总：

| 指标                     | 计算或用途                                             |
| ------------------------ | ------------------------------------------------------ |
| 输入 token               | `prompt_cache_hit_tokens + prompt_cache_miss_tokens` |
| 缓存 token 命中率        | `hit / (hit + miss)`                                 |
| 有缓存命中的请求占比     | 区分“偶尔命中很长前缀”和“多数请求稳定命中”         |
| 输出 token               | 判断总成本是否主要来自输出                             |
| Schema 重试率            | 检查拆分消息后结构遵循是否变化                         |
| 各任务成功率与输出一致性 | 防止只看价格忽略模型行为变化                           |
| 一次性例子 token         | 估算例子替换造成的尾部重算规模                         |

计算成本时分别使用命中输入、未命中输入和输出单价，不使用固定“命中按 0.1 倍”之类的近似说法。

建议至少比较三个窗口：

1. 改造前的真实基线。
2. 先改 `evaluate_explanation + generate_teaching` 后的观察期。
3. 四个任务全部切换后的观察期。

## 十、实施步骤

完全没有先后依赖并不现实，三类请求都要先具备相同的消息和快照契约。本方案只保留一个不改变模型行为的公共基础步骤；基础完成后，评价、教学、支持三个业务步骤互不依赖，可以分别提交、验证和回退。暂不抽取共享的“上下文组装器”，避免一个任务的改动牵动其他任务。

### 步骤 0：统计改造前基线

本步骤不修改生产代码，也不依赖后续步骤。

新建：

- `ljg_docs/12-提示词共享前缀/02-DeepSeek缓存基线统计.py`：只读解析 `external_call_records.raw_response`，按 taskType、模型和 `promptVersion` 汇总命中 token、未命中 token、输出 token 与结构重试率。
- `ljg_docs/12-提示词共享前缀/03-DeepSeek缓存基线结果.md`：记录统计时间范围、样本量、无法解析的记录数和结果表。

验收：脚本不写数据库；随机抽取若干记录，手工核对 usage 字段与统计结果。

### 步骤 1：建立公共契约，不改变现有请求

这一提交只让数据结构能够表达五层消息，四个任务仍按原样发送单条 user 消息，因此可以单独上线和回退。

### 步骤 2：迁移 `evaluate_explanation`

## 十一、验证门槛

每个业务迁移步骤上线前都要满足适用于该 taskType 的条目：

- 五层消息顺序与审计快照一致。
- 共享 system 不包含题目、状态值、学生文本、当前原因和例子。
- 同一题目上下文多次序列化的内容和字段顺序一致。
- 同一历史快照切换 taskType 时，前三层保持一致。
- 历史新增条目时不回写旧条目，只在末尾追加。
- 结构重试时只改变本轮任务数据，不改写前四层。
- A 原因例子换成 B 后，下一轮请求中找不到 A 例子原文。
- JSON Schema 校验与业务字段校验全部通过。
- 对连续 user 消息执行一次真实 DeepSeek 或当前代理端点集成测试。

上线后的判断不设“命中率为 0 就自动降级”。由人工综合比较：

- 缓存 token 命中率及费用。
- Schema 重试率。
- 输出一致性和教学质量回归。
- 请求快照与排障复杂度。

如果缓存收益很低，但多消息结构让职责和审计更清楚，也可以保留。若模型行为明显退化，应先检查消息边界、模板重复和代理兼容性，再决定回退。

## 十二、不采用的方案

### 12.1 合并为一个多任务提示词

不采用。四个任务的输出字段、终态规则和职责不同。合并会让每次请求携带无关指令，扩大字段串扰和回归范围，也削弱独立版本管理。

### 12.2 只新增 `system_message` 字段

不采用。`ModelTransportSnapshot.messages` 已经可以表达真实请求。再增加平行字段会出现“审计字段是一套、最终传输又是一套”的双重真源。

### 12.3 只改模板文件组织，不改消息顺序

可以改善维护，但不是缓存无效。即使仍是一条 user 消息，只要开头内容稳定，DeepSeek 同样可以缓存。当前选择拆分消息，是为了明确语义边界、提高跨任务前缀复用，并让审计结构与真实请求一致。

### 12.4 保留旧例子换取缓存

不采用。旧例子可能把已经变化的原因继续带入教学生成。这里以模型可见语义正确为先，只接受动态尾部重新计算。

### 12.5 直接复制 DeepSeek Harness 或 Claude Code

不采用。两者解决的是长时 Agent 会话、工具结果和上下文压缩问题。当前项目暂未证明需要同等复杂度。这里只吸收稳定前缀、原生角色、真实顺序、确定性视图和用量观测这些原则。

## 十三、合理性批判与不足

1. **五层消息不保证立刻提高命中率。** DeepSeek 只命中已经落盘的完整前缀单元。短请求、首次请求或紧接着发出的并发请求可能来不及复用缓存，必须以 usage 数据为准。
2. **题目材料前置有额外输入成本。** 如果某些任务并不需要完整题目材料，为了共享前缀一律发送会浪费 token，甚至增加无关信息干扰。实施时要先确认真正的跨任务交集。
3. **共享 system 会扩大规则变更的影响面。** 原因定义或全局边界一旦修改，四个任务会同时改变缓存前缀和模型行为。共享内容应保持最小，并通过 `promptVersion` 和回归样例控制变更。
4. **缓存优化可能不是最高收益项。** `deepseek-flash` 的输出价格显著高于命中输入价格。如果现有成本主要来自冗长输出或结构重试，减少输出 token、提高一次成功率可能更值得优先处理。
5. **全量历史仍可能带来噪声。** 10 轮对话通常不需要压缩，但无关内容、旧任务要求或模型早期错误仍可能干扰当前任务。全量保留只适合作为当前阶段的简化方案；如果回归测试发现干扰，应先裁掉无关历史，再考虑摘要。
