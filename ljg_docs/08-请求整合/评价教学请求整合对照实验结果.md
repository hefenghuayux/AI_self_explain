# 评价(evaluate_explanation) 与 教学(generate_teaching) 请求整合对照实验

编写日期：2026-09-15

实验目的：评估把原来「评价」与「教学」两次模型调用合并为一次调用的可行性，以及字段在不同拆分粒度下的效果与耗时。直接构造请求调用模型（DeepSeek），不启动项目。

## 环境

- 模型：`deepseek-flash`（.env 中配置的 `deepseek-v4.1-flash` 在当前 API 上不可用，可用名称经探测为 `deepseek-flash` / `deepseek-v4-pro`）
- 接口：`https://api.deepseek.com/chat/completions`
- 温度：0.3；response_format：`json_object`
- 三个实验共用同一条题目（题库 question id=3）和三组学生自讲回答，仅字段拆分与调用次数不同

### 题目材料

> （高一数学·二次函数，中等）已知函数 f(x)=x²−2ax+2a−1（a∈R）。当 x∈[0,2] 时，f(x) 的最大值为 3。求实数 a 的所有可能取值，并求每种情况下 f(x) 在区间 [0,2] 上的最小值。

评分点（rubricPoints）：

1. 指出二次函数图像开口向上，因此区间 [0,2] 上的最大值必在端点 x=0 或 x=2 处取得
2. 正确计算 f(0)=2a−1，f(2)=3−2a，并建立 max{2a−1, 3−2a}=3
3. 分类讨论两个端点取得最大值的情形并校验另一端点不超过 3，得到 a=0 或 a=2
4. 分别代入 a=0 和 a=2，求出区间最小值均为 −1，并说明对应取值点

### 三组学生回答（用户回答）

| 编号               | 学生自讲文本                                                                                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-有进展正确不完整 | 这题二次函数开口向上，因为 x² 系数是 1 大于 0。闭区间 [0,2] 上的最大值应该在端点 x=0 或 x=2 取到。先算 f(0)=2a−1，f(2)=3−2a，然后令 f(0)=3 得 a=2，这时候 f(2)=−1。最大值就是 3。 |
| B-错误理解         | 开口向上，所以最大值在顶点取得。顶点 x=a，f(a)=−a²+2a−1。令最大值等于 3，解出 a。然后最小值也是顶点那里。                                                                          |
| C-无进展表述不清   | 我不知道，感觉就是差不多，不知道最大值怎么算，也不会分类。                                                                                                                            |

> 说明：以上三组用户回答均构造自项目 `回答记录.txt`（真实对话片段）的场景，覆盖「正确但补全不完整 / 概念性错误 / 无进展表达不清」三类典型情况。

## 实验一：evaluate 输出 3 项 + teach 输出 5 项（两次调用）

### 拆分配置

- 调用 1（评价）：`correctness, completeness, hasProgress`

## 汇总对比

| 维度                 | 实验一（3+5，两次调用） | 实验二（6+2，两次调用） | 实验三（8 合一，一次调用） |
| -------------------- | ----------------------- | ----------------------- | -------------------------- |
| 模型调用次数/例      | 2                       | 2                       | 1                          |
| 评价占比             | 轻（3 字段）            | 中（6 字段）            | 重（8 字段一次给）         |
| 迟到原因依赖         | 教学调用需等待评价结果  | 教学调用需等待评价结果  | 无中间依赖                 |
| 平均耗时（3 例均值） | **5928 ms**       | 8253 ms                 | 5987 ms                    |
| 内容完整性           | 完整                    | 完整                    | 完整                       |
| 字段一致性           | 需串联两次输出          | 需串联两次输出          | 天然一致                   |

### 关键发现

1. **合并（实验三）并不比实验一更快**：实验三单次调用平均 5987 ms，与实验一两次调用合计 5928 ms 几乎持平，甚至略高。原因是合并后单次输出要包含全部 8 个字段，`deepseek-flash` 作为推理模型在同一 token 预算内既要做推理又要输出完整 JSON，单次耗时被拉高；而实验一虽然两次调用，但每次输出被拆细、单次更轻。
2. **合并方案的 token 预算风险（必须注意）**：首次运行实验三时使用 `max_tokens=1500`，该推理模型把全部 1500 tokens 都花在 `reasoning_content` 上，导致 `content` 字段为空（A、B 两组失败）。只有当 `max_tokens` 提高到 4000 时才正常输出完整 JSON。**这说明：走合并路径时，必须给合并调用配置显著更大的输出预算，否则结构校验会失败。**
3. **实验二最慢（8253 ms）**：调用 1 输出 6 个字段（评价 + 详尽 judge_reason），推理最重；调用 2 只输出 2 个字段但耗时并不低（约 4.7 s）。把原因分类放进评价步并不能显著提速，反而因为单次输出更大而更慢。
4. **字段注入有效**：实验一/二的调用 2 都直接把上游结果注入提示词，模型没有重复推理正确性/完整性/进度，也未出现与上游矛盾的内容。说明「下游注入上游结果」的拆法可行。
5. **质量一致**：三个实验在「有进展正确不完整」与「错误理解」两组上都给出了正确的评价和有效的追问/纠错，未出现合并后质量劣化（除 token 预算不足的配置问题外）。

### 结论：能否合并？

**可以合并，且合并本身不牺牲质量，但要满足两个前提**：

- ① 合并调用必须配置足够大的 `max_tokens`（本实验为 4000），避免推理模型把预算全花在 reasoning 而产出空 content —— 这是合并路径的硬性要求，否则结构校验失败率会显著升高。
- ② 若目标是省时，**一次合并调用（实验三）并不比「评价拆 3 项 + 教学拆 5 项」的两次调用更快**；它省的是「一次 HTTP 往返 + 中间等待 + token 缓存命中」的代价，而不是绝对延迟。

从工程角度更推荐**实验一的拆分（评价 3 项 + 教学 5 项）**，理由：

- 每次调用更轻、token 预算要求更低，结构失败概率更小；
- 教学调用能在拿到评价后独立重试，容错更清晰；
- 实测耗时与一次合并几乎持平。

若业务强依赖「单次调用」以省往返/简化审计，可选用实验三方案，但必须提高输出预算并做充分的空 content 兜底。
