# 评价教学合一步实施方案

## 变更概述

将 `submit_text_attempt` 入口的**评价 + 教学两次模型调用合为一次**。模型一次返回评价字段和教学内容。规则简化：有进展时按正常策略输出；无进展时无论正确性全部改为提示。后端不做教学内容二次校验，直接使用模型输出。

---

## 新的动作决策规则

模型在 prompt 中同时看到 `coveredPointsCurrentRound`（本轮已覆盖评分点）和它自己要输出的 `coveredPoints`，可以直接判断"有没有新点"。

| 正确性 | 完整性 | 有新点 | 模型输出的教学内容 |
|---|---|---|---|
| CORRECT | COMPLETE | — | `content: null, questions: []` |
| CORRECT | INCOMPLETE | ✓ | `content`（聚焦追问正文）, `questions: [{question}]` |
| CORRECT | INCOMPLETE | ✗ | `content`（提示正文）, `questions: []` |
| WRONG | COMPLETE | ✓ | `content`（纠错正文）, `questions: []` |
| WRONG | COMPLETE | ✗ | `content`（提示正文）, `questions: []` |
| WRONG | INCOMPLETE | ✓ | `content`（纠错+追问正文）, `questions: [{question}]` |
| WRONG | INCOMPLETE | ✗ | `content`（提示正文）, `questions: []` |
| UNCERTAIN | 任意 | — | `content: null, questions: [], needHumanReason: "原因"` |

新点定义：模型输出的 `coveredPoints` 不在 `coveredPointsCurrentRound` 中。

---

## 后端仍然保留的确定性逻辑

以下规则不变，不由模型控制：

1. **支持上限检查**：`support_count_round + 1 ≥ first/second_round_support_limit` → 忽略模型输出的教学内容，展示完整解析
2. **COMPLETED 进入**：`correctness=CORRECT + completeness=COMPLETE` → 终态
3. **UNCERTAIN 进入**：`correctness=UNCERTAIN` → NEED_HUMAN
4. **覆盖点追踪**：更新 `covered_points_current_round`、`covered_points_all`、`no_progress_count`
5. **流阶段转换**：各阶段之间的切换
6. **会话版本冲突**：防止重复提交
7. **Schema 结构校验**：枚举值、字段类型、errorEvidence.quote 必须在 confirmedText 中

---

## 后端移除的逻辑

1. ~~`decide_teaching()` 中的无进展动作升级判断~~（已移入 prompt）
2. ~~`AITeachingService.generate()` 调用~~（不再有第二步模型调用）

```
你是 AI 自讲 Demo 的评价与教学生成器。

## 第一阶段：评价
（保留原有的评价指令：评估正确性、完整性、评分点覆盖、错误证据）

    你输出的 coveredPoints 如果包含 coveredPointsCurrentRound 中没有的点 → 有新点。

  | 评价结果 | 有新点 | 输出 |

  | WRONG + INCOMPLETE | 有新点 | content（纠错加一个追问方向）+ 1 个追问问题 |
  | WRONG + INCOMPLETE | 无新点 | content（一个提示），不要出问题 |

约束：
- 不得直接复述标准答案或完整解析
- CORRECT+COMPLETE 和 UNCERTAIN 时 content 必须为 null，questions 必须为 []
```

### 3. Service 层

**`backend/app/services/ai_evaluation.py`** — 新增合并输出的解析路径

```python
def _parse_merged_output(
    content: str,
    rubric_points: list[str],
    confirmed_text: str,
) -> tuple[MergedModelOutput | None, list[str]]:
    try:
        payload = json.loads(content)
        # coveredPoints 整数化处理（与现有 _parse_and_validate_evaluation 相同）
        if isinstance(payload, dict):
            legacy_points = payload.get("coveredPoints")
            if isinstance(legacy_points, list) and all(
                isinstance(point, str) for point in legacy_points
            ):
                payload["coveredPoints"] = [
                    rubric_points.index(point) + 1 for point in legacy_points
                ]
        output = MergedModelOutput.model_validate(payload)
    except (ValidationError, ValueError, TypeError) as error:
        if isinstance(error, ValidationError):
            return None, [entry["msg"] for entry in error.errors()]
        return None, [str(error)]
    # 评价字段关系校验（复用现有 validate_evaluation_relationships）
    errors = validate_evaluation_relationships(output, rubric_points, confirmed_text)
    if errors:
        return None, errors
    return output, []
```

```python
def submit_text_attempt(...):
    # … 前置校验、保存 attempt …
    
    # 一次模型调用
    merged_raw = call_model_with_merged_prompt(...)
    merged = parse_merged_output(merged_raw)

        # 直接完成
        ...
    elif decision.next_status == "SHOWING_FULL_SOLUTION":
        # 支持上限 → 展示解析，忽略模型的教学内容
        ...
    elif decision.next_status == "NEED_HUMAN":
        # 人工处理
        ...
    else:
```

## 合理性批判与不足

1. **规则硬编码进 prompt 之后，更改触发条件、新增分支或调整阈值都需要修改 prompt 并发布。** 你已接受这个代价。但如果后续频繁改规则（比如"无进展"的定义从"无新评分点"变成"无新评分点且文本长度增加不到 30%"），prompt 会越来越复杂，不如确定性代码好维护。建议把"这条规则是否适合长期放 prompt"作为一个监控点，如果一个月内改过两次，就考虑移回后端。

2. **无进展时 WRONG+COMPLETE 也改成给提示。** 当前代码里 WRONG+COMPLETE 的动作是 GIVE_CORRECTION，没有走无进展升级路径。改成无进展时给提示，意味着"学生说错了但完整，无进展"——这场景在现实中可能存在（学生每次写错了但每次都写一样的东西）。为这种场景直接出提示而不是纠错，可能错过一次精确纠错的机会。如果你的学生数据中这种模式不常见，可以接受。

3. **后端不做教学内容校验。** 意味着模型泄露完整解析、直接给答案、或 question 数量不符合预期时，后端不会拦截。如果这种问题偶尔出现，学生看到不合适的教学内容，但业务流程仍然正常推进（不会崩溃）。这是一个质量风险而非功能风险。如果你后续发现这类问题较多，可以考虑加轻量校验（只拦截，不重试，走 NEED_HUMAN）。

4. **覆盖点追踪仍然由后端维护。** `no_progress_count` 用于审计和统计，不用于动作决策。这样即使模型在"有无新点"上判断失误，统计数据仍然是客观的。这个设计保留得好。

5. **支持上限和 COMPLETED、UNCERTAIN 三种情况仍然由后端覆写。** 这是安全兜底。即使模型输出了教学 content，一旦触发支持上限，后端仍然展示完整解析。这个安全闸没有松。
