# 题库导入决议与实施方案

## 1. 目的与范围

本文固化将原系统题库接入 AI 自讲的已确认决议，并给出当前阶段的实施计划。

本阶段不实现题库爬取、原库写入或自动同步。原系统数据库继续是题目基础内容的来源；AI 自讲材料及会话数据只保存在独立的 AI 自讲数据库中。现有 SQLite 的 AI 自讲历史数据需要迁移到新 MySQL，并保留原主键与关联关系。

## 2. 已确认决议

### 2.1 数据库边界

- 在现有 MySQL 主机上新建独立数据库 `ai_self_explain`。
- `ai_self_explain` 承载 AI 自讲的全部表，包括用户、认证会话、题目、自讲会话、评价与日志。
- 创建 AI 自讲专用最小权限应用账号；高权限 `devuser` 只用于运维建库和迁移，禁止写入项目 `.env`。
- 原系统库 `tbox_test` 只读，不创建表、不修改 `tiku_question`、不写回 AI 自讲材料。
- 本阶段不使用网页爬虫；导入程序直接从 `tbox_test.tiku_question` 读取。
- 不做自动或定时同步。导入完成后的源库变更不会自动覆盖 AI 自讲数据。

### 2.2 导入范围

- 只导入 `tiku_question.del_status = 0` 的题目。
- 本次盘点该范围共有 30,545 条题目；数量以实际导入开始时的查询结果为准。
- `self_explain_questions` 包含 `新表.md` 中定义的 AI 自讲与来源映射字段，不建立完整的 `tiku_question` 字段镜像表，也不额外保留原库状态和时间审计字段。
- `self_explain_questions` 替代现有 `questions` 表；`sessions.question_id` 的外键迁移到新表。
- `tiku_question_id` 保存原题 `id`，允许为 `NULL`；非空值必须唯一。手工录入题目和迁移的历史本地题目可以没有外部题库 ID。两个数据库之间不建立数据库级外键。
- 原库中没有对应信息，或对应源字段值为空时，AI 自讲侧保存 SQL `NULL`，不以空字符串、空数组或模型生成内容伪造来源数据。

### 2.3 字段映射

| 原库 `tiku_question` | AI 自讲 `self_explain_questions` | 迁移规则 |
| --- | --- | --- |
| `id` | `tiku_question_id` | 原值复制；非空值唯一 |
| `content` | `question_content` | 原值复制，保留 HTML |
| `display_answer` | `standard_answer` | 原值复制；为空时保存 `NULL` |
| `analysis` | `full_solution` | 原值复制；为空时保存 `NULL` |
| `grade_period` | `grade_period` | 原值复制 |
| `subject` | `subject` | 原值复制 |
| `q_type` | `q_type` | 原值复制 |
| `difficulty_level` | `difficulty_level` | 原值复制 |
| `review` | `review` | 原值复制 |
| `topics` | `topics` | 原值复制 |
| `method` | `method` | 原值复制 |
| 无对应字段 | `rubric_points` | 初始为 `NULL` |
| 无对应字段 | `common_errors` | 初始为 `NULL` |
| 无对应字段 | `alternative_solutions` | 初始为 `NULL` |
| 无对应字段 | `layered_hints` | 初始为 `NULL` |
| 无对应字段 | `guided_questions` | 初始为 `NULL` |
| AI 自讲内部字段 | `id`、`archived_at`、`created_at`、`updated_at` | 由 AI 自讲数据库生成和维护 |

`answers` 不映射到 `standard_answer`。该字段在原库中是原始 JSON 格式答案；本阶段的学生可读标准答案固定采用 `display_answer`。原始 `answers` 不在本阶段新表字段范围内。

### 2.4 缺失材料与自讲规则

题目材料缺失不阻止学生使用该题自讲。系统必须区分以下两种确定性模式：

| 模式 | 判定条件 | AI 评价与完成规则 |
| --- | --- | --- |
| `FULL_RUBRIC` | `rubric_points` 为非空 JSON 列表 | 沿用现有“正确且完整才完成”的规则；覆盖与缺失评分点按题目评分点集合校验 |
| `BASIC` | `rubric_points` 为 `NULL` 或空 JSON 列表 | AI 基于题干、`standard_answer` 和 `full_solution` 评价正确性；正确即完成；结果和审计必须标记“未配置评分点” |
| `AI_GENERAL` | `rubric_points` 为空，且 `standard_answer`、`full_solution` 均为 `NULL` | AI 仅依据题干和自身知识评价正确性；正确即完成；结果和审计必须标记“无人工评价依据” |

题目列表排序以“是否存在非空 `rubric_points`”为第一排序键：有评分点的题目排在前面，随后按既有业务排序规则处理。`rubric_points` 的空值判断必须由数据库或后端确定性代码完成，不能由 AI 判定。

当 `standard_answer` 与 `full_solution` 同时为 `NULL` 时，仍允许学生发起自讲，并使用 `AI_GENERAL` 模式。该模式的完成结果不能与 `FULL_RUBRIC` 混合统计或展示。

### 2.5 现有实现的必要调整

当前 `Question` 模型和 API 输入契约将评分点、常见错误、替代解法、分层提示和完整解析设为非空；这与本方案的 `NULL` 导入规则冲突。实施时必须同步调整：

1. MySQL 表模型与迁移中的可空性。
2. 题目录入、读取和编辑 API 的 Schema。
3. AI 评价请求构造、输出校验与会话完成规则。
4. 前端题目列表排序和学生可见的基础自讲标识。

不能仅放宽数据库列的 `NULL` 约束；若 API、提示词和规则层仍假定评分点必有，缺失材料题目会在运行时失败或产生错误完成结论。

## 3. 实施计划

### 第 1 步：创建独立数据库与连接配置

1. 创建 `ai_self_explain`，显式使用 `utf8mb4`、`utf8mb4` 排序规则和 InnoDB。
2. 为 AI 自讲应用创建独立、最小权限的数据库账号 `ai_self_explain_app`；高权限的 `devuser` 只用于运维操作，禁止写入项目 `.env`。
3. 将后端数据库连接能力从当前仅接受 SQLite 的配置扩展到 MySQL，并增加 `PyMySQL` 运行时依赖。

完成标准：应用能用专用账号连接空的 `ai_self_explain`，且不能对 `tbox_test` 执行写操作。

### 第 2 步：建立题目表与基础自讲数据契约

1. 新增 `self_explain_questions` 模型和 Alembic 迁移，字段以本文件第 2.3 节为准；迁移既有 `questions` 表并将 `sessions.question_id` 外键切换到新表。
2. 使来源字段和 AI 自讲补录字段支持 SQL `NULL`；对 `tiku_question_id` 设置唯一约束，允许多条 `NULL`。
3. 在规则层实现 `FULL_RUBRIC`、`BASIC` 与 `AI_GENERAL` 三种模式，明确各自的完成事件与审计标记。
4. 调整题目列表查询，以非空评分点优先排序。

完成标准：含 `NULL` AI 材料的题目可被保存、读取和进入正确的自讲模式；含评分点题目保持原有完整性规则。

### 第 3 步：实现一次性只读导入

1. 编写显式命令，从 `tbox_test.tiku_question` 按 `id` 升序、分批读取 `del_status = 0` 的记录。
2. 严格按第 2.3 节字段映射写入 `self_explain_questions`，不清洗 HTML，不调用 AI 生成缺失字段，不修改源库。
3. 导入日志记录开始时间、源查询条件、读取数、插入数、失败题目 ID 和具体错误。
4. 重复运行时跳过已存在的 `tiku_question_id` 并记录，不更新任何来源字段或 AI 自讲人工补录字段。其他导入失败保留明确错误；不以吞错或默认值继续写入。

完成标准：目标表的唯一 `tiku_question_id` 数量与源查询数量一致，且可抽样逐字段核对题干、答案和解析。

### 第 4 步：验证、切换与人工补录

1. 为字段映射、`NULL` 保留、唯一约束、列表排序和两种自讲模式补充单元及集成测试。
2. 核对导入总数、`display_answer` 与 `analysis` 的空值数量，以及 HTML 题干未被改写。
3. 将现有 SQLite 的全部 AI 自讲表迁移到 MySQL，保留历史主键与关联关系；历史本地题目写入 `self_explain_questions` 时 `tiku_question_id` 为 `NULL`，验证数据数量和外键引用。
4. 将题目读取入口切换到 `self_explain_questions`，验证原有录题、会话、评价、日志和权限流程。
5. 由录题人员在 AI 自讲侧补录评分点等材料；补录后题目自动进入 `FULL_RUBRIC` 模式。

完成标准：测试通过；导入统计可复核；题目在无评分点和有评分点两种情况下均能得到符合规则的结果。

## 4. 决策完成状态

本阶段产品与数据契约决策已完成，可以进入实现准备。创建数据库、创建账号、修改代码和执行导入属于后续实施操作，必须在获得明确实施授权后按本文件的四步计划执行。

## 6. 题目列表分页与检索决议（2026-08-27）

题库导入后，活动题目达到三万条量级。题目列表不能再一次返回完整题干、答案、解析和 AI 材料；列表读取改为确定性的后端分页与摘要数据契约，详情读取继续使用既有单题接口。

### 6.1 列表查询契约

- `GET /api/questions` 直接替换原数组响应，返回 `{ items, pagination }`。前后端同轮发布，不保留并行的旧数组接口。
- 查询参数为 `page`（默认 `1`）、`page_size`（默认 `20`，范围 `1` 至 `100`）、`grade_period`、`subject`、`keyword` 和既有的 `include_archived`。
- `grade_period`、`subject` 和 `keyword` 同时出现时采用 AND 条件；空白 `subject`、`keyword` 视为未筛选。
- `keyword` 在保留原始 HTML 的 `question_content` 中进行参数化、字面包含检索。`%`、`_` 和反斜杠必须转义，不能改变为 SQL 通配符。
- 列表排序保持“非空 `rubric_points` 优先，其后按 `created_at`、`id` 倒序”；计数查询和当前页查询必须复用同一筛选条件。
- 摘要项只包含 ID、题干、学段、学科、题型、难度、评价方式、评分点数和归档时间；不返回标准答案、完整解析、复习说明、主题、解题方法或 AI 材料。`GET /api/questions/{id}` 仍返回完整题目。

### 6.2 动态筛选选项与权限

- `GET /api/questions/filter-options` 从 `self_explain_questions.grade_period` 和 `subject` 读取非空去重值并排序，不在前端硬编码学段或学科。
- 学生只能读取未归档题目及其筛选选项；教师传 `include_archived=true` 后，列表和筛选选项同时扩展到归档题目。
- 筛选选项只随当前归档可见范围变化，不因关键词或已选筛选条件而收窄，避免筛选控件的候选值跳动。

### 6.3 前端行为

- 页面首次加载筛选选项和第 1 页题目；修改学段、学科、关键词或归档范围时回到第 1 页。
- 前端只渲染当前页的桌面表格和移动卡片；使用每页 `20`、`50`、`100` 的分页控件。
- 页面显示学段原始数值和学科原始编码。若要显示“小学”“数学”等中文名称，必须先提供原系统编码的权威映射，不能由 AI 或前端猜测。

### 6.4 导入题干的 HTML 显示

- `question_content`、`standard_answer` 和 `full_solution` 保持导入时的原始 HTML，录题表单继续以原文编辑。
- 列表、详情和自讲页显示上述内容时，前端必须先通过同一 HTML 净化模块移除脚本和事件属性，再以 HTML 方式渲染；题干图片按容器宽度缩放。

## 7. 合理性批判与不足

1. 一次性复制降低了对原系统运行时可用性的依赖，却会造成题目基础内容逐渐陈旧；后续需要另行评估人工重导机制。
2. `BASIC` 模式提升了题目覆盖率，但评价缺少可审计评分点，结果可信度和可解释性低于 `FULL_RUBRIC`。
3. 仅映射 `display_answer` 会舍弃原始 `answers` 的结构化信息；若后续需要选项级判定或多答案处理，应先扩展数据契约后再导入。
4. 当前数据库账号拥有极高权限；在专用低权限账号落地前，任何应用侧连接都存在误操作与凭据泄露风险。
