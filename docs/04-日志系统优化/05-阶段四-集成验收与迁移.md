# 阶段四：集成验收与迁移

## 1. 阶段目标

验证前三阶段形成的完整日志链路，验收阶段一已经实现的 Structured Event v2 到 v3 导出迁移，确认模型请求快照、业务事件、运行日志和前端人读视图相互一致，并完成最终文档与交付检查。

本阶段不新增功能，只修复验收中发现的本方案范围内问题。

## 2. 准备修改的准确路径

根据验收结果，只允许修改前三阶段已经涉及的文件，以及：

- `backend/tests/integration/test_sessions.py`
- `backend/tests/integration/test_learning_timeline.py`

如果需要修改本列表之外的业务模块，必须先说明原因、影响并等待确认。

## 3. v2 到 v3 导出迁移

### 3.1 问题

当前 `trace.jsonl` 使用 eventId 去重后增量追加。Schema v3 删除、重命名和合并了事件，如果继续向旧文件追加，会形成 v2/v3 混合文件，并保留已删除的 `student.input.confirmed`。

### 3.2 验收决策

审计导出在阶段一已经改为数据库权威事实的全量可重建投影，因此本阶段验证：

1. 读取现有 `trace.jsonl` 第一条有效记录的 schemaVersion；v3 每行是 `{schemaVersion, producer, sessionId, event}` 独立记录信封。
2. 如果历史文件不是 `3.0`，确认阶段一的导出逻辑已从当前数据库全量重建 v3 内容。
3. 确认先写入同目录临时文件。
4. 确认写入、刷新和校验成功后原子替换 `trace.jsonl`。
5. `audit.md` 同样从当前 trace 全量重建并原子替换。
6. 不在一个 JSONL 文件中保留两种 Schema，且后续导出不再增量追加。

不得通过忽略版本继续追加，也不得尝试把旧事件字符串原地改写成 v3。

### 3.3 历史请求快照

旧 `ExternalCallRecord.request_snapshot` 为 NULL 时：

- v3 AI 事件保留调用结果；
- 明确标记历史请求内容不可用；
- 不根据当前题目、当前模板或当前会话状态重新渲染历史请求；
- 人读界面显示“历史记录未保存请求快照”。

## 4. 全链路验收场景

### 4.1 文本自讲成功

验证：

- 只有一个 `student.explanation.submitted`；
- 同时引用 attempt 和 submission；
- 提交状态转换存在；
- 模型请求快照包含学生输入；
- AI 调用、输出校验和评价后状态转换完整；
- `transportStatus` 与 `validationStatus` 分别正确，不能把 Schema 错误显示成传输失败；
- 人读视图压缩为 2 至 3 个主要步骤。

### 4.2 AI Schema 重试

验证：

- 每次真实调用有独立 externalCallRecord 和 requestSnapshot；
- 第二次请求包含第一次 validationErrors；
- `ai.call.completed` 与 `ai.output.validation_failed` 不被误判为重复；
- 每条调用的 `transportStatus`、`validationStatus` 和 `validationErrors` 与事件一致；
- 人读视图显示调用次数和最终结果；
- Structured Event 能逐次展开。

### 4.3 AI 传输失败

验证：

- timeout、连接错误和 HTTP 错误都有明确 error；
- 不输出无意义 null 字段；
- 已发起请求的快照仍被保存；
- 最终重试耗尽后的人工复核状态转换存在；
- 运行日志显示明确 ERROR/WARNING，但不打印完整 prompt。

### 4.4 语音自讲

验证：

- ASR 调用、音频落盘、语音转写和最终提交关系正确；
- 未提交语音草稿只产生 transcription 事件；
- 最终提交后产生 `student.explanation.submitted`；
- 人读视图将音频和转写技术细节折叠进语音步骤；
- requestId 贯穿 WebSocket、ASR 和后续提交的可关联范围。

### 4.5 教学支持与疑问

验证：

- AI_SUPPORT 和 GUIDED_ANSWER_ASSESSMENT 请求快照 purpose 正确；
- mainDraft、doubtText、questions 和 answers 分块正确；
- support.generated 与对应状态转换可关联；
- `requestId` 和 `relatedSupportEventId` 能确定性关联教学支持调用、支持记录和状态转换；
- 完整解析和标准答案只在教师审计中出现。

### 4.6 暂停、恢复与人工复核

验证：

- 不涉及 AI 的状态转换不会出现空 duration/error/source；
- 人读视图准确表达暂停、恢复和人工复核原因；
- Structured Event 保留 before/after snapshot。

## 5. 安全验收

必须搜索并验证以下内容不会进入普通运行日志：

- AI API key；
- Authorization header；
- 学生完整输入；
- 标准答案和完整解析；
- 模型请求快照；
- 未来 memoryContext 内容。

同时验证：

- 审计路由仍要求教师身份；
- 导出目录被 `.gitignore` 排除；
- 错误日志不会通过异常对象意外打印 HTTP Authorization header；
- 请求快照 privacy 元数据与实际包含内容一致。
- 普通运行日志使用紧凑文本，不与旧 JSON 内容混写；旧文件已按约定保留并归档。

多教师或多学校部署前的会话归属授权属于当前必须登记的风险，但如果本阶段没有对应产品身份模型，不擅自扩展权限系统。

## 6. 性能与容量验收

记录以下结果，不设未经验证的固定阈值：

- 单次评价 request_snapshot 字节数；
- 一次含重试会话的 trace API 响应大小；
- `audit.md` 和 `trace.jsonl` 文件大小；
- 生成和导出 trace 的耗时；
- 前端展开长提示词时的交互表现。

如果完整请求导致明显响应膨胀，先报告数据，再决定是否增加详情懒加载接口；本阶段不预先实现额外接口。

1. 更新全链路日志字段说明到 Schema v3。

- 最终回复说明提交哈希、提交信息、当前分支和是否推送。

## 9. 最终验收标准

- 机器事件完整、稳定、无无意义空字段。
- 人读日志和审计视图简洁，正常流程无需展开原始 JSON 即可理解。
- 模型请求内容可按规则、题目、会话、记忆、用户输入和重试上下文查看。
- 保存的 transport payload 与实际发送内容一致。
- v2/v3 不混写，历史无法还原的内容不被伪造。
- 普通日志无敏感模型上下文。
- 所有测试、迁移、构建和视觉检查通过。

## 10. 合理性批判与不足

1. 全量重建导出依赖数据库仍保留权威记录；如果数据库记录已被清理，旧导出中的信息无法完整恢复，因此实施前应确认当前数据保留策略。
2. 完整请求快照让审计更可信，但 trace API 响应可能变大；只有在测量确认存在问题后才值得增加懒加载，避免提前引入接口复杂度。
3. 当前教师角色校验不足以覆盖未来多租户归属隔离。本阶段按单教师本地 Demo 验收，但不能据此宣称已经满足生产隐私要求。
